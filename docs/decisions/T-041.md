- D-159 · 2026-11-10 · The agent keeps its desired list with clear secret values in `state_dir/desired.json` (file 0600, directory 0700, owner is the agent user, atomic write). This confirms D-037 and D-089. The condition: a resource type writes every attribute to the guest in the same form as the desired list holds it, so the list holds what the guest holds. Two exceptions are accepted, because root on the guest sees these values in the command bodies of the agent anyway: (a) a resource with `state: absent` keeps its other attributes in the list (for example the secret `content` of a `file`), and the guest does not hold them; (b) an apply stores the new list before it changes the guest, so after a failed or refused step the list holds the new value until the next apply or `watch`. All resource types of today meet the condition (`user` has no password attribute). A new type or attribute whose guest state is a derived form of a secret (password hash, database user, entry in a key store) must not put the clear value into the stored list. First choice: the attribute takes the derived form (for example `password_hash`, and the secret holds the hash). A type that must get the clear value needs its own decision before it merges; the direction is: the agent does not store this attribute and keeps the state that it observed after its own apply as the reference for the drift check, while `observe` and `apply` bodies still carry the value for the exact compare. No keyed hash and no question to the controller on drift. The agent never logs or sends the list. A `watch` replaces the list, so a resource that is no longer desired leaves the file; `seal` deletes it (D-098). A re-enrollment drops only the credential: the list stays, and the drift check continues, until the next `watch` replaces it. When a target is removed and its guest is not destroyed, the file stays on that guest, as the managed files do. The agent deletes left-over temp files of the list (`.desired.json-*`) at start, and `seal` deletes them too. Known limit: the value is on the guest disk and in guest backups, also when the managed file is on tmpfs · the agent must find drift alone, also when the controller is down and after a guest restart (D-028); root on the guest reads the managed file and gets the value in every apply anyway; the key of a keyed hash would lie next to the list, so root and a stolen backup get both, and a hash without a key is refused (D-037); a question to the controller makes the drift check depend on the controller and sends the secret more often (T-041 finding F1)
