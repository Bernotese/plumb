- D-188 · 2026-11-11 · Plumb keeps no binding from an Image to its template. Every guest create calls `Driver.FetchImage` with the Image document of the Run's revision and clones the template that the driver returns; the driver reuses the template of that name and checksum or imports it again (D-077). A migration removes the old `Image` rows of `binding`. The Plan does not say if a download is needed, and a fetch needs no approval of its own. Plumb still never removes a template or an import file, also not when a Plan deletes the Image document; removal comes with the retention of T-039 (D-098). The rest of D-077 stays (names, pool and range check, reuse of the import file) · the binding was a cache that nothing cleared: it was stale after an Image delete, a checksum change, or a `qm destroy` of the template (T-015 run 3); `FetchImage` is idempotent and costs two calls; the approved Image document pins the checksum, so a second fetch gives the same file; a template is a cache (D-014)
- D-189 · 2026-11-11 · The create-only attribute `image` of `guest:config` is the name of the Image document, not the driver ref. `GuestSpec.ImageName` carries it; the Proxmox driver writes `plumb-image: <Image name>` into the guest description (replaces the template VMID of D-077) and reads it back. `GuestSpec.Image` is only the clone source of `Create`; `Diff`, `DriftGuest` and `Observe` do not use it. A new checksum or a re-made template changes nothing on a guest that exists; a Target whose `spec.image` names another Image is still refused. Guests made before this change do not exist outside tests, so there is no conversion · a re-made template gets a new VMID, and with the VMID as identity every guest of the old template would fail every Plan and show destructive drift; an image is a cache and a new image version changes no target (D-014, D-098); the name is observed on the hypervisor, so the check needs no store state
