- D-390 · 2026-11-14 · accepted (pl-backend, T-190; pl-lead and pl-architect; D-383, D-385, D-387 made concrete; replaces "`agent.json` names `token_file: /etc/plumb-agent/enroll.token`" of ARCHITECTURE §19). The repair bundle and the install command put a new token only into the one-shot file `/etc/plumb-agent/enroll.token` (root, 0600); `install.sh` keeps the token source of `agent.json` (a VM: SMBIOS serial; an LXC: its `token_env`), so a later re-enrollment works as before. At its start the agent reads the file and deletes it at once, whatever comes next; a file that is not a regular file of the agent's user with mode 0600 (no group or other bits, no symlink) is ignored and deleted too. The agent enrolls with the token before it uses the stored credential; only a successful enrollment replaces the credential. A refused token (expired, used, unknown) is dropped and the old credential stays; a controller out of reach keeps the token in memory for 15 minutes, then drops it, and the old credential stays. The token is never logged. Plan origins `repair` and `adopt` come with migration 0021 (`plan` rebuild, as 0019); the repair key and the host key pins move to 0022 (T-191), the adoption reserve to 0023 (pl-lead). The install script and the bundle builder live in `internal/link/agentinstall` (a sub-package of `link`, so ARCHITECTURE §2 is unchanged) · a token file named in `agent.json` would replace the SMBIOS or `env` source for good and break the re-enrollment of a repaired guest; a stored credential that is still valid (an agent that was only cut off) must not win over the repair token, and a failed repair must not drop it (review R1 of #290)
