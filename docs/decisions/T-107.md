- D-288 · 2026-11-13 · proposed (pl-architect, T-107; user question 2). A backup is one file: an online SQLite snapshot of the whole database (revisions, Plans, Runs, Issues, bindings, agent identities, secrets as stored) plus the link directory (CA certificate and key). The Proxmox token secret (`plumb.env`) and the master key are never in it (D-177). Format: a clear header (magic, format version, created time, install id, a fingerprint of the backup key) and the body in chunks, each sealed with AES-256-GCM under a key derived from the master key (HKDF, own label); the header is the AAD of every chunk, with the chunk index and a last-chunk flag, so nothing can be cut, reordered or swapped and a wrong recovery key is named before any decrypt. `serve` writes it to `/var/lib/plumb/backups` (0600, owner `plumb`) on a schedule (default daily 03:00, keep 7) and on `POST /backups` (admin session or a token with `apply`); `GET /backups` lists name, time, size, SHA-256, the result of the last run and the state of the off-host copy; there is no download route. Each backup is an event · the export has no bindings or agent identities, so a Plumb restored from it would make new guests; the CA key must not lie in clear on a backup storage; one GCM over a growing database would need it all in memory
