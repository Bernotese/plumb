- D-221 · 2026-11-11 · accepted (pl-lead). Known limit of the linked-clone guard of `RemoveImage` (review S3): Plumb always makes full clones. A linked clone that someone makes by hand in Proxmox is not seen by the Plumb token on lvmthin: the clone's disk line has no `base-…/` prefix and the volume list has no `parent` (only root's `lvs` shows the origin). There `RemoveImage` removes the template, and Proxmox allows it; the thin clone keeps its data (proven on the host, T-061 log). On storages where the token sees a sign, `RemoveImage` refuses; where Proxmox itself refuses the delete, Plumb reports that error. On every storage type the token's volume list holds only the Plumb pool's volumes, so a linked clone **outside** the pool is never seen (review N1 of PR #136). The flow test accepts the lvmthin case · lvmthin is the installer's disk storage; a new right to read the origin would need `Sys.Audit` or root, and the removal does not break the clone
- D-222 · 2026-11-11 · accepted (pl-lead). `MakeImage` regenerates the cloud-init drive of the version (`PUT …/qemu/<id>/cloudinit`) after the write that clears the build values, also when it finishes a template (`nameVersion`). Before, the version template's drive kept the build guest's user-data (user and host name `plumb-build…`, the vendor parts; T-061 finding B). After it the drive holds only the version name as host name. A failed regeneration fails `MakeImage` before the conversion, and the guest gets its build name back; on the template path (`nameVersion`) the template gets its build name and marker back too, so it is never a version with the old drive (review S1 of PR #136). A clone gets its own empty drive and writes its own data at the start (proven on the host). T-066 also scans the template's cloud-init volume · a delete and a new drive needs `VM.Config.CDROM`, which the token does not have (D-081); "regenerate" needs only `VM.Config.Cloudinit` and works on a template too
