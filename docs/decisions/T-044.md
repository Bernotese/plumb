# T-044 decisions

Decided: the user approved the plan on 2026-11-10 (D-176, PR #77). `pl-lead` appends the lines to `docs/DECISIONS.md` after the merge of T-046 and deletes this file.

- D-167 · 2026-11-10 · A Block can have `spec.after`: a list of resource ids (`type:key`; literal strings, not templates; `uniqueItems`, at most 16). Each use of the Block starts only when every named resource of the same Target has ended. This is the only new order rule: uses with no `after` relation still run in parallel, and list position has no meaning (D-027 stays). The name is a resource id, not a Block name and not a use id. The Target gets no `after` field · the Block author knows what the Block needs, so the user declares nothing and cannot forget it (D-165). Resource ids are already the names that `restart_on` uses across Blocks (D-036, D-053). An edge to a whole use means "after its last step"; for `nginx` that is `service:nginx`, and `service:nginx` must wait for the site (D-172). A use-level name would make a cycle for the one Block that needs the feature
- D-168 · 2026-11-10 · Save-time checks of `after`. Block document: the type of each id must be an agent resource type (not `guest`). Target render: each id must be a rendered agent resource of this Target and must belong to another Block use; else `state.Render` fails at `/spec/blocks/<i>` with a text that names the Block, the use and the id. After that, render builds the wait graph of the Target (the step before in the same use, `restart_on`, `after`) and fails on a cycle with a text that names two resources of the cycle. One function in `internal/wire` builds this graph; `state.Render` and `agent.plan` both use it. The agent keeps its own check before an apply (D-055). The cycle check runs for every proposed state (`state.Validate`: proposal, rollback, import). `state.Load` of a stored revision does not run it: the controller starts and serves as before, logs one warning per Target with a cycle, and the applies of that Target fail at the agent as today. The next proposal of any kind is refused with the cycle text and the Target name until it also repairs the cycle · errors surface when a document is saved, not at apply time (D-053). One function means one rule (as `wire.ActionOf`, D-047). This also moves the `restart_on` cycle of D-055 to save time. `Load` of the head revision runs before every proposal (`plan.Propose`), so a `Load` that refuses a stored cycle would also refuse the proposal that repairs it (review S3)
- D-169 · 2026-11-10 · Wire format: `wire.Resource` gets `after` (list of resource ids, omitted when empty). `state.Render` sets it on the first resource of each use whose Block has `spec.after`. `ApplyBody`, `Planned`, the reports and the database do not change; there is no migration. An agent that is older than this change ignores the field and runs the uses in parallel as before; the controller has no version gate · one general edge ("this step waits for these steps") is the smallest change of the step graph, and the field travels with every resource list. No agent is installed on a real host yet, and a first Run on an old agent fails in a visible way and the next Run repairs it; the gate belongs to the agent self-update card
- D-170 · 2026-11-10 · Agent execution and skip rule. The graph function returns each edge with its kind (step before in the same use, `restart_on`, `after`), and a step of the agent keeps two lists: `needs` (`after`) and `restartDeps` (`restart_on`). Only `restartDeps` feed `resource.RestartChange`: a service that is the first resource of a use does not restart because its `after` resource changed. A step with `needs` waits until every named step has ended. It runs only when each of them ended `unchanged` or `applied`. When one ended `failed`, `refused` or `skipped`, the step is `skipped` with the output `not applied: <id> was <status>`, and the rest of its use is skipped by the rule that exists (D-075). Every skipped step now has an output that names the resource that caused the skip, also after a failure inside its own use. When the context ends during the wait (apply timeout, stop), the step and the rest of its use are `skipped` with `not applied: the apply ended while this resource waited for <id>`, and `apply` returns with no goroutine left. So the skip passes down a chain of uses, and uses with no relation to the failure run to the end. A `restart_on` edge keeps its meaning: the service waits, restarts when a listed resource changed, and still runs when one of them failed. An `after` id that is not in the resource list fails the apply before anything runs, like a duplicate id or a cycle. `after` is order only: when an override sets the named resource to `state: absent`, the save passes, the Plan shows the removal, and the dependent can fail at the apply; there is no check for that · `after` means "needs"; a step on a broken base fails with a confusing error (missing parent), and a skip names the real cause. `restart_on` means "react to"; one broken site must not stop the service for the other sites. Two lists keep "needs" apart from "react to" (review S1); a Run view with empty skipped rows explains nothing (review N1)
- D-171 · 2026-11-10 · How the user sees the order. `ResourcePlan` gets the optional field `after` (resource ids) in `api/openapi.yaml`; the controller copies it from the render. The Plan keeps its list order; the Plan view shows "after `package:nginx`" on the resource. `ResourcePlan` also gets the optional field `restart_by`: for a service with a planned `restart` change, the ids from its `restart_on` that have a change in the same Plan or are left out of the observe (D-156, D-160), in `restart_on` order. The controller computes it from the render and the Plan; it is display only and not part of `wire.Planned` or `wire.Covers`. The Plan view shows "restart because of `file:/etc/nginx/sites-available/a`". A skipped step of a Run shows the output of D-170. `ResourcePlan` and `RunStep` get no Block field and `run_step` gets no column · the Plan must show the order (card), and a label on the one resource that waits does that without a new grouping of the Plan view. The Run view already has an output column. With `restarts` (D-172) a Block can add a restart trigger to a service of another Block, for example `service:ssh`; the approver must see the cause of each restart (D-022, security note of the plan review). The resource id names the cause; a use id would need a Block field on `ResourcePlan`
- D-172 · 2026-11-10 · A Block can have `spec.restarts`: a list of service ids (literal strings `service:<name>`, not templates; `uniqueItems`, at most 16). `state.Render` adds the ids of all resources of this Block use to `restart_on` of each named service, in Target order, after all Blocks are rendered and before the overrides. It skips the service itself and ids that are already in the list. The merged list keeps the JSON form (`[]any` of strings), and one helper (`wire.RestartOn`) reads `restart_on` in render, `plan.plannedRestarts`, `resource.RestartChange` and the agent. A named service that is not on the Target is a render error that names the Block use. An override of `restart_on` still replaces the full list (D-053). The agent sees a normal `restart_on` (D-036) and the Plan shows the restart. Render order: Blocks, `restarts`, overrides, type schemas, `restart_on` check, `after` check, cycle check · a Block has a fixed resource list and cannot add to `restart_on` of another Block; with an override the user had to repeat all ids, and a missed id gave a site that was applied but not active (first D-165 draft, PR #73). The render check and `plannedRestarts` cast `restart_on` to `[]any`; a `[]string` would pass the check without a look and lose the planned restart of D-160, and the apply would then be refused as not planned (review S2). `restarts` keeps the `^service:` pattern and `maxItems: 16`
- D-173 · 2026-11-10 · The starter Block `nginx-site` comes back (file in `sites-available`, link in `sites-enabled`; params `name`, `server_name`, `root`, `state`) with `after: [package:nginx]` and `restarts: [service:nginx]`. On a Target without the `nginx` Block the save fails and names `package:nginx`. First Run on a new Target: `package:nginx`, then the default site and all sites in parallel, then `service:nginx` once. The rule of D-165 stays (a starter Block must apply clean in the first Run on a new Target); its sentence "T-020 ships no `nginx-site` Block and no `spec.restarts` field" ends with this card · the site needs only the directory that the package creates, not the running service
- D-174 · 2026-11-10 · Acceptance test of the order feature, in the CI guest job: `TestGuestNginxSitesFirstRun` (`internal/agent`, tag `guest`). It removes nginx and `/etc/nginx`, renders a Target with `nginx` and two `nginx-site` uses from the real files in `blocks/` (new `blocks.FS`, `go:embed`), and gives the agent one apply command with every resource `unverified`. No step is `failed`, `refused` or `skipped`, and each site answers with its own page (`Host` header). It runs for both Target orders (sites before `nginx`, `nginx` before sites). A second test without Docker is the proof of the race: the slice fixture creates `/etc/nginx` only when the fake package install runs, with a delay, and the test fails when `after` is removed from the Block (mutation). It has two paths: a new Target (all `unverified`), and an enrolled Target without nginx that adds `nginx` and two sites, so the Plan has real planned changes and `wire.Covers` must match after the wait (D-075). Agent tests cover the skip rule, the two edge kinds and a context that ends during the wait (D-170) · the unit and slice tests of T-020 did not see the race because the fixture made the directories first and the guest test called the resources one by one (review of PR #73). The guest test alone cannot prove the race, because its result depends on apt timing (plan review S4, S5)
- D-175 · 2026-11-10 · Not part of `after` now: an `after` field on a Block use in the Target, a Block name or use id as a name, templates in `after` or `restarts`, and a reverse order for removal. Each can come later without a break: a Block name has no `:`, so the two name forms can never collide · no real Block needs them (D-027), and the Target form has no raw mode, so a per-use field needs new form work
