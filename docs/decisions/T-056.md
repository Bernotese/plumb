- D-194 · 2026-11-11 · Makes D-193 concrete. A Target has the setting `spec.allow_restart` (boolean, default `false`, changeable by a normal proposal; the name and the default are proposals until the user confirms them). `false`: no Run stops or restarts this VM while it runs. `true`: a Run may restart it. It stands next to `guest`, not in it, because it is a rule of Plumb and no Proxmox value: it is never drift and has no override. A change of the setting has no risk of its own and is not human-only. One pure rule serves Plan and Run. Guest stopped: a change of `cores` or `memory` is written, no restart, no start. Guest running and `true`: the Plan gets the `restart` change (risk `disruptive`) on `guest:config` when a value of `cores` or `memory` changes or already waits, with the text "Restart of the VM if Proxmox cannot apply the change live: clean shutdown, hard power-off after 2 minutes, then start."; the Run writes, observes, restarts once (D-078), also when the Plan re-enrolls, and skips the restart when nothing waits; a Run without a planned restart fails before a write instead of restarting; a restart that fails ends the step with a text that names the observed power state, with no retry and no second power action; a value that still waits after a restart fails the step; the resource steps wait for a new `hello`. Guest running and `false`: the Run writes the value and sends no power action; the change has `waits_for_restart: true` in the Plan and in the step, and the step is `applied`. A re-enrollment (D-038) of a running VM with `false` is refused at the proposal with a text that names the two ways (set `allow_restart` in the same proposal, or stop the VM first); a stopped VM is re-enrolled as before. No type of VM exists as a document yet: when Target templates exist, the template gives the default. LXC: the field is valid and has no effect yet · the costs of a wrong default differ: a value that waits is visible and one restart fixes it, a VM that went down cannot be undone; `false` is also the behaviour before this card, so no existing Target changes; a setting with the name "allow restart" that let a re-enrollment restart the VM would break its own promise, and the token of a re-enrollment lives 15 minutes, so it cannot wait for the user; the restart stays a `disruptive` change of its own, so a token never restarts a VM above its `max_risk`, whoever switched the setting
- D-195 · 2026-11-11 · "A value waits for a restart" (D-193) is a state of the Target, not an Issue. It is defined by the three views of D-190 alone: the running value differs from the desired one and the value after the next cold start is the desired one; who wrote it does not matter. `driver.WaitingGuest` lists these values, `DriftGuest` does not, and the guest poll reports `unchanged`. The list is stored with the binding (`binding.waiting`, migration 0007) and written with the digest: when the digest moves, and at the end of every Run for each of its Targets with a guest. The API shows it as `TargetStatus.waiting` and as the phase `restart_needed` (after `drifted`, before `ready`); an event marks each change of the list. A change that waits carries `waits_for_restart: true` (`wire.Change`); the run step stays `applied` (no new status in D-045); the Issue of a revert that ends this way is `resolved`. The state ends when (1) the user stops and starts the VM outside Plumb (the next poll round sees it, no Plan), (2) a Run restarts it after `allow_restart` became `true`, (3) the desired value goes back to the running one (the Plan removes the waiting value, D-191), or (4) someone changes the waiting value outside Plumb (then it is drift). Risks, changing D-063: every write of `cores` or `memory` is `reversible`; the `restart` change carries `disruptive`; `bridge` and `enroll_token` stay `disruptive` · nobody acted against the desired state, so there is nothing to accept or revert, and an Issue that only a restart can close would stay open for weeks on a VM that must not go down; the three views need no memory of who wrote a value, so the state is right after a controller restart and after a `qm set` by a person; a write that does not touch the running guest disrupts nothing, and a risk that depends on the power state would refuse a step when the guest stops between Plan and Run
