- D-195 · 2026-11-11 · "A value waits for a restart" (D-193) is a state of the Target, not an Issue. It is defined by the three views of D-190 alone, for `cores` and `memory` only: the running value differs from the desired one and the value after the next cold start is the desired one; who wrote it does not matter. `driver.WaitingGuest` lists these values, `DriftGuest` does not. For `bridge` and the create-only inputs the same views are drift; a `bridge` that still waits after a write fails the step. The list is stored with the binding (`binding.waiting`, entries `{attr, from, to, since}`, migration 0007) and written with the digest: in the guest poll when the digest moved or the stored list is not empty, and at the end of every Run, succeeded or failed, for each of its Targets with a guest. Migration 0007 also empties every stored digest, so the first poll round after the upgrade compares every guest. The API shows the list as `TargetStatus.waiting` and as the phase `restart_needed` (after `drifted`, before `ready`); the web shows the list and its age also in every other phase; an event marks each change of the list. "Succeeded" never hides a waiting value: a change that waits carries `waits_for_restart: true` (`wire.Change`) and the run step stays `applied` (no new status in D-045); the Run carries the number of such changes (`Run.waits_for_restart`); an Issue of `guest:config` that is resolved (`gone`, `revert`, `accept`) while the list is not empty gets a `system` comment that names the waiting value, and its event carries the number. The state ends when (1) the user stops and starts the VM outside Plumb (the next poll round sees it, no Plan), (2) a Run restarts it after `allow_restart` became `true`, (3) the desired value goes back to the running one (the Plan removes the waiting value, D-191), or (4) someone changes the waiting value outside Plumb (then it is drift). Risks: D-063 stays. A write of a new value of `cores` or `memory` is `disruptive`, also when it only waits; only the removal of a pending value is `reversible` (D-191); the `restart` change is `disruptive` · nobody can accept or revert a value that is already set, and an Issue that only a restart can close would stay open for weeks on a VM that must not go down; the three views need no memory of who wrote a value, so the state is right after a controller restart and after a `qm set` by a person; a write that waits decides what the VM is after its next cold start, and that start can come with no Plan and no approver (host maintenance, HA), so a token below `disruptive` must not make it (review S3); the stored digests already cover pending values, so without the reset old waiting values stay unseen; the end of the state must not depend on a digest that moves (review S7, S8)
