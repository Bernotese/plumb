- D-395 · 2026-11-14 · accepted (pl-architect, T-204; host finding F5 of T-192; refines D-373, D-386). **How other Plans behave:** an approval commits the revision before the Run (D-022); a Run that fails keeps it. A Target create whose clone fails leaves its document without a binding (phase `pending`/`error`), and the next Plan that touches it plans a create again: the desired state stays ahead of the guest until a Run gets there. An adopt Plan is the same at the revision level, but its "retry" is not safe: binding needs the checked request (node, VMID, name, digest) of a human-approved adopt Plan. **Decision:** a refused adopt Run keeps its document as a clear **not-adopted** Target (`TargetStatus.not_adopted`, "not adopted: the guest changed"). (1) Two Target documents never claim the same `adopted.node/vmid`: a Propose that adds a second claim is refused with 409 `adopt-claimed` (a pair already in the base is tolerated so the head stays plannable). (2) Only a new adopt Plan through `POST /targets/{name}/adopt` binds it, human-only and with all checks again; under the guest's (new) Proxmox name it removes the not-adopted Targets of the same guest in the same Plan, under the same name it replaces the document. Every other Plan that touches it (a named Target, a document or Block change, a token Plan) plans and runs **nothing** for it and says so in a note. (3) Its delete has no binding, so it makes no Proxmox call and never touches the guest. (4) The Target page shows the state with both actions; the Targets list marks it "not adopted" · a refused adopt that commits nothing would need a second commit rule for one origin; a clear state with one way in keeps D-022 and closes the double claim
