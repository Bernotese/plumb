- D-315 · 2026-11-13 · proposed (pl-backend, T-112; D-302 made concrete). Backup runs are rows of the table `backup_run` (migration 0014: started, finished, result `running`/`ok`/`failed`, by, file name, message); `GET /backups` shows the newest as `last_run` and `running` from it. Only one run at a time (a lock in `serve` and the store refuses a second running row; 409 `backup-running`). A running row at the start of `serve` was cut by a stop and becomes `failed` ("interrupted"); temp files `.tmp-*` of the backup dir are removed then. A backup holds its own row as `running` (the snapshot is taken inside the run). `BackupRun.name` is set only for `ok`. A failure is the event `backup.finished` with `result: failed` and the message in `last_run` (no Issue) · the contract asks for the event; one row per run keeps the history in the database without a new Issue kind
- D-316 · 2026-11-13 · proposed (pl-backend, T-112). Schedule: a check every minute; the backup of a day is due when today's `--backup-time` (UTC) passed and no backup by `system` started since that time, so a controller that was down at the time catches up at its start; a manual backup does not count for the schedule, a failed scheduled one is not tried again until the next day. Retention after every good backup: keep the newest `--backup-keep` files by name time (and `-n`), scheduled and manual together, never the one that `latest` names; the `.sha256` goes with its file. `--backup-time`/`--backup-keep` default from `PLUMB_BACKUP_TIME`/`PLUMB_BACKUP_KEEP`, checked at start (HH:MM; 1 … 90) · catch-up covers a host that sleeps at 03:00; no retry loop that could fill the disk
- D-317 · 2026-11-13 · proposed (pl-backend, T-112). Writer and reader: the master key bytes stay in `internal/secret` (`Key.BackupDataKey(salt)`, `Key.BackupFingerprint()`, labels checked against `internal/backup` by a test). `backup.Read` (for T-113) checks the fingerprint first (`ErrWrongKey`), then opens each chunk (the last-flag is part of the nonce, so a missing, extra, reordered or foreign chunk fails), checks the four tar entries in order and the manifest sizes against the header, and reads to the end; a full last chunk is allowed. The database entry is `VACUUM INTO` a 0600 temp file in the 0700 backup dir, removed after the run. Logs hold only the file name and error texts, never key material or data. The header takes `PLUMB_INSTALL_ID`, `PLUMB_PVE_NODE`, `PLUMB_PVE_POOL` from the environment (empty in a dev install until T-114 writes them) · one place holds key bytes; the reader that T-113 needs is tested here against cut and changed files. Also (for T-114): `plumb backup now [--data DIR] [--key-file F] [--wait 15m]` writes one backup beside a running `serve`, not through a local socket (ARCHITECTURE §16 says "CLI wrapper of POST /backups on the local socket"; there is no such socket): it opens the same database (WAL), checks the master key against it, takes the header fields (`install_id`, `node`, `pool`, `agent_url`) from `<data>/backups/install.json` that `serve` writes at every start (no secret), waits while another backup runs, and exits 0 only when the file is written (1 else, 2 usage); by `system`. Only `serve` cleans temp files and fails cut runs · the installer runs it with `pct exec` without the flags and environment of `serve`; a new socket would be new attack surface
