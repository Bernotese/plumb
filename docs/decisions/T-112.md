- D-316 · 2026-11-13 · proposed (pl-backend, T-112; REPLACES the D-316 text in DECISIONS.md: retention by run order, review L3 round 2 of #220). Schedule: a check every minute; the backup of a day is due when today's `--backup-time` (UTC) passed and no backup with trigger `schedule` started since that time, so a controller that was down at the time catches up at its start; a backup of `POST /backups` or `plumb backup now` does not count for the schedule (`plumb backup now` acts as `system`, which is the only principal for it in the contract, so the trigger tells them apart; review L2 of #220), a failed scheduled one is not tried again until the next day. Retention after every good backup: keep the newest `--backup-keep` files by the order of their runs (`backup_run.id`; name time and file time both follow the clock, so a clock step back would sort a new backup as old, review L3 of #220 round 2); a file without a run row counts as the oldest, scheduled and manual together, never the one that `latest` names; the `.sha256` goes with its file. `--backup-time`/`--backup-keep` default from `PLUMB_BACKUP_TIME`/`PLUMB_BACKUP_KEEP`, checked at start (HH:MM; 1 … 90) · catch-up covers a host that sleeps at 03:00; no retry loop that could fill the disk
