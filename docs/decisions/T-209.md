- D-397 · 2026-11-14 · accepted (pl-architect, T-209, host finding F10; D-384 made concrete). Host key pins and the repair report belong to one binding generation, not to a Target name or VMID: `binding.gen` comes from a counter (`binding_seq`, migration 0024) that never repeats; a new binding or a new ref gets a new one, the same ref keeps it. The rows carry `guest_id = '<ref>@<gen>'`; `DeleteBinding` and a `PutBinding` with a new ref drop them in the same transaction; a pin or report for a generation that is not live is not written (a report that raced the delete), and `host-key-shared` counts only live pins, so a real clone of two live Targets is still refused. Migration 0024 removes the rows of deleted Targets and of older guests. A parked guest (D-396) loses its rows with the binding at the delete; its agent's reports are dropped by the link, and its key line is tracked in `unbind_pending.key_ids`. The delete also ends the Target's open Issues (gone, by system, with the reason as a comment; no report could resolve them, D-211) and drops `issue_ignore` and `ignored_drift`; it keeps what the copy rule needs: the stored value hashes for their retention (D-331) and the value cap flag with its `agent:values` Issue until the flag ends (D-353), so a deleted and remade Target stays human-only · pins tied only to the name or VMID let a reused VMID or name inherit another guest's trust (fails closed today, as `host-key-shared`/`no-pin`, but blocks repair)
