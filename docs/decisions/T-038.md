# T-038 decisions (PROPOSED, pl-architect, 2026-11-12; accepted only with the user's approval of the plan)

- D-224 · 2026-11-12 · proposed (pl-architect, T-038). An LXC Image names a Proxmox system template by URL (`http://` or `https://`) and pins its SHA-512 (`sha512`, 128 hex; `sha256` is not allowed for `lxc`); VM Images stay `https://` + `sha256`. The controller downloads the file itself and checks the pin before it parses anything. Plumb does not read the appliance index; the docs list the values of the supported templates and the host command that prints them from the index cache that `pveam update` verified. Refines "checksum of the appliance index" of D-097 · Proxmox serves templates and index only over http (the https name does not match, host A2); the index is signed and holds only `md5sum` and `sha512sum`; a pin in the revision needs no OpenPGP code in the controller
- D-225 · 2026-11-12 · proposed (pl-architect, T-038). New dependency `github.com/klauspost/compress/zstd`, the decoder only, with `WithDecoderConcurrency(1)`, `WithDecoderMaxWindow(128 MiB)`, `WithDecoderMaxMemory(256 MiB)`, closed on every path incl. a cancel; the 4 GiB unpacked limit counts decoder output; the repacked output is `.tar.gz` with the standard library · every Proxmox system template is `.tar.zst` (host A1); Go has no zstd reader; Proxmox creates containers from `.tar.gz` (host B3)
- D-226 · 2026-11-12 · proposed (pl-architect, T-038). An LXC Target has no bootstrap user: `user` is refused; `ssh_keys` go to `root` with the create parameter `ssh-public-keys` and are create-only; a named user comes from a Block such as `deploy-user` · Proxmox has no cloud-init for containers; one path for users
- D-227 · 2026-11-12 · proposed (pl-architect, T-038). Plumb makes only unprivileged containers with `features=nesting=1` and no other feature, no `lxc.*` key, no mount point and no device; Observe refuses to manage a container without `unprivileged: 1`, and a feature other than `nesting=1`, an `mpN`, `devN` or `lxc.*` line added outside Plumb is a `guest:config` Issue (revert only for `features`). `nesting=1` means the AppArmor profile `lxc-container-default-with-nesting`, own `proc`/`sys` mounts, and some host `/proc`/`/sys` content visible in the container; root stays uid 100000 on the host; it is the Proxmox UI default · least privilege for root in the guest (uid 100000 on the host); Ubuntu 26.04 has no network and 17 failed units without nesting, Debian 13 is degraded (host D4)
- D-228 · 2026-11-12 · proposed (pl-architect, T-038). The `symlink` resource has no fallback when `renameat2` flags are not supported (`EINVAL`, e.g. ZFS before 2.2): it fails with a text that names the directory, the flags and ZFS ≥ 2.2 · a plain `rename` loses the race protection of D-163; ext4 in a container supports both flags (host D3)
- D-229 · 2026-11-12 · proposed (pl-architect, T-038). `plumb-images` holds content `import,vztmpl`. The start check of D-183 accepts exactly the set `{import}` (warning; an LXC Image fails with "run install.sh again") or `{import, vztmpl}`; the installer's storage rule (D-084) accepts both. A new install sets both. Upgrade: the repair run of the new `install.sh` shows the content change, asks, pushes the new binary first, then sets the content, then restarts the controller; its dry run says that `pvesm set` reorders the content lists of other storages. Rollback: when the restart of the new binary fails, the installer sets the content back to `import` before it restores an old binary; a person who restores an old binary by hand runs `pvesm set plumb-images --content import` first (docs and failure text) · no new storage and no new role (`Datastore.AllocateTemplate` covers the upload, host B1); today's controller refuses the new content with exit 78 (host G0), so the binary must change first
- D-230 · 2026-11-12 · proposed (pl-architect, T-038). Repack: the base blocks are copied byte-exact up to the end of the last entry; appended as USTAR entries (uid 0, fixed mtime): `/etc/plumb-agent/` with `ca.pem` and `agent.json` (`token_env`), the first-boot script `/usr/local/sbin/plumb-agent-install` (the script of the vendor snippet, D-082), the units `plumb-agent-install.service` and `plumb-agent.service` with their wants links; no agent binary. Names are normalised (strip `./`, `path.Clean`, no trailing `/`) and the last entry of a name decides. The base is refused when it has a Plumb path, a parent whose last entry is not a directory (links count), a device node or fifo, none of curl/wget/python3, a truncated stream, or more than 4 GiB of decoder output / 500 000 entries. The first-boot script copies the binary to a temp name and renames it (also in the vendor snippet), and its unit has no `ConditionPathExists`; a controller that is down at the first boot is recovered by the re-enrollment Plan. A reused file is trusted by name (writers of `plumb-images` = the Plumb token and root); a create that fails with an archive error uploads the file once more and tries once again. Name `plumb-ct-<image>-<d12>.tar.gz`, `d` = SHA-256 over pinned SHA-512, CA, agent URL and the pack format version; upload with a `Content-Length` and the SHA-256 checksum parameter · no header round trip (Ubuntu has GNU long names, host A3); a template does not change with an agent release (as D-206), which matters because the token cannot delete a file (host B4)
- D-231 · 2026-11-12 · proposed (pl-architect, T-038). The enrollment token of a container is the `env` entry `PLUMB_ENROLL_TOKEN` at create and at re-enrollment; the agent reads it from `/proc/1/environ` (`token_env` in `agent.json`); after the hello the Run step `guest:bootstrap` removes `env` (`ClearBootstrap`, pending until the next restart on a running container) · D-025 made concrete; works with today's rights (`VM.Config.Options`, host C2); only PID 1 holds the value and only root reads it (host C3); Proxmox shows `env` only to `VM.Config.Options` holders and in no task log (host C2)
- D-233 · 2026-11-12 · proposed (pl-architect, T-038). Plumb never deletes an LXC template file (`vztmpl`), as import files (D-209): retention and Image delete never call `RemoveImage` for one; `unused_imports` of the Image status lists an unused file with its `pvesm free <storage>:vztmpl/<file>` line, for `lxc` Images with or without `build`. A file is unused when its name does not match the current pin, CA and URL · the token gets 403 without `Datastore.Allocate` (host B4), and that right would let it change the storage; with D-232 an expected 403 must not fail a step
- D-234 · 2026-11-12 · proposed (pl-architect, T-038; only if the user says yes to LXC image builds). An LXC build container is created from the repacked file; before `POST …/template` the container is stopped and `ClearBootstrap` is applied (`…/config` and `…/pending` hold no `env`), and every clone create sets its own `env`; `seal` in a container skips the cloud-init, dracut and `fstrim` steps (no cloud-init, no initramfs, FITRIM is not permitted, host D5), removes the agent state dir and credential and the SSH host keys, adds a first-boot unit that runs `ssh-keygen -A` when a key is missing, ordered `Before=ssh.service ssh.socket sshd-keygen.service` (Ubuntu 26.04 uses socket activation), and empties `/etc/machine-id`; the version is a container template (`POST …/lxc/<id>/template`), Targets are full clones; D-221 holds for containers (the token sees no linked clone, host C6) and D-232 for retention · a clone keeps the SSH host keys of its template while Proxmox makes a new machine-id (host D1)
- D-235 · 2026-11-12 · proposed (pl-architect, T-038, review S1). The human-only reason `image-recipe` (D-201) also covers creating an `lxc` Image and changing its `url` or `sha512`: only a human session approves a Plan that makes the controller fetch from a new address or trust a new pin · the controller itself fetches the URL (D-237) and the pin is the only trust boundary of the rootfs (D-224)
- D-236 · 2026-11-12 · proposed (pl-architect, T-038, review B1). Hard limits of an LXC template fetch in the controller: the download stops at 1 GiB and at its `Content-Length`; the unpacked tar stops at 4 GiB (decoder output); before the fetch and after every 64 MiB written, the free space of `/var/lib/plumb` must stay at or above 2 GiB. Every stop removes both temp files and fails the step `image:fetch` with one text that names the limit and the numbers. The upload needs 2 × the file size free on `plumb-images` · the temp files share the root fs with the database (6.7 GB free on the test host); an http sender controls the body size; templates are 130 … 160 MB (host A1)
- D-237 · 2026-11-12 · proposed (pl-architect, T-038, review S1). The controller's template fetch: `http`/`https` only; the dialled address is checked after DNS (`net.Dialer.Control`): loopback, link-local (incl. `169.254.169.254`), unspecified and multicast are refused, private LAN addresses are allowed; no redirects; no auth header, cookie, body or environment proxy; errors show status and size, never the body; 15 min per download · VM images are fetched by Proxmox (`download-url`), LXC templates by the controller (it must repack them), so the controller gets a new outgoing path that must not reach itself or metadata services or read LAN services through Plumb
