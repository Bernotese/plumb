- D-232 · 2026-11-12 · accepted (pl-architect, QA finding of T-065). Retention after a good build sorts its errors in two classes. A template that retention keeps on purpose because it is in use is left and named in the output, and the step `image:retention` is `applied`: a version pinned by a running create, and the `RemoveImage` guard refusals "linked clones" and "locked" (they wrap the new `driver.ErrImageInUse`). Every other `ListImages` or `RemoveImage` error (and a store error after a removal) makes the step `failed` and the Run `failed`; the output still names what was removed and left, and ends with `<err>; v<N> is ready and usable; old templates stay until the next build`. When only the store row of a removed template failed, the line is `version N: the template is removed, the store row is not: <err>; v<N> is ready and usable; the next build fixes the store row` (D-198 heals the row). The new version stays `ready` and usable; the next build tries the removal again · before, every guard refusal and every API error was a "left" line in an applied step, so a broken removal (rights, API, storage) was never seen; a template in use is normal and must not fail a build
