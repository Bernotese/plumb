## 5a. Acceptance lists and scopes (review of #385)

### P1: R1 = the clean install with a restore (last part of C7)

Steps, in this order on `pve-dev`, with the RC tarball:

1. The state before: every test Target of C7 is `ready` with its agent online. Record the Target list, the users, the token names (never their bearers), the open Issues, the ACL view (rows), and the guest backup list of each Target.
2. A Plumb backup (`plumb backup now` as the `plumb` user) and an export.
3. The old controller off: `install.sh --remove --keep-guests` (dry run → pl-lead → go). The guests keep running.
4. A clean install from the RC tarball (its `SHA256SUMS` checked by C3's code), on the same LXC id, with the usual flags (dry run → pl-lead → go).
5. `plumb restore` of the backup of step 2, then the restore confirm by a person (D-303).

Acceptance list:

- [ ] Every Target of step 1 reconciles: its Run or poll ends with no change, and **no drift Issue** opens within 15 minutes.
- [ ] Every agent reconnects (online) without a re-enroll, and the pinned host keys stay.
- [ ] The users log in; every token of step 1 works within its tier; a revoked one stays revoked (401).
- [ ] The guest backups of step 1 are still listed under "this guest", and one of them restores (a guest with a data disk).
- [ ] The NIC Target on `vmbr9` and the data disks are as before (no Plan proposes a change).
- [ ] Rights unchanged: the ACL view equals step 1 (rows), and `storage.cfg` is byte-equal.
- [ ] No secret in the logs of the new controller (C5b reads them).

### P2: the O1 probe loop (in C9)

One test runs the firewall test's listener and probe **about 200 rounds inside one job**: once in the LXD container job and once in the guest VM job, **first after boot** (before the other tests). Each round has a fresh listener and a connect probe with a 5 s limit that tells a timeout from a refusal; the first failure writes the T-250 dump. It is its own test (`TestGuestFirewallProbeLoop`, about 2 minutes), so it adds no job and no rerun. A failure with the dump → a fix card. 0 of about 400 → the release notes name O1 as unexplained.

### P3: cross-machine reproducibility (in C1)

C1 builds one commit twice: `package-release.sh` on the dev VM, and the same script in a CI job on the C1 branch, which uploads `SHA256SUMS` as an artifact (no release, no tag, no run of the release workflow).

- Equal `SHA256SUMS` → C10 compares the draft's sums with C7's RC, as planned.
- Different → C1 says why, and fixes it if the fix is small. Else C10 **tests the workflow's own artifact**: download the draft's tarball, check `gh attestation verify` and `sha256sum -c`, and run the install/upgrade smoke on `pve-dev` (an upgrade from the C7 RC, then the R1 acceptance list once) before the user publishes.

### P4: the scope of pl-reviewer's cards (C5a, C5b, C9)

- **Exact values:** the scan tool reads the values from the 0600 files under `~/.config/plump/` (`testhost-api.token`, `testhost-recovery.key`, `testhost-admin.pw`, and any `t*-secrets.json` still there) inside the tool, and compares by file. A value never appears on a command line, in an argument list, in a log, or in the report.
- **Scanner:** `gitleaks` (pinned version; its default rules plus Plumb's patterns: `tok_…`, Plumb bearers, `PVEAPIToken=`, private key blocks) over every ref (`git fetch origin '+refs/*:refs/remotes/all/*'`, `refs/pull/*` included), plus the exact-value compare over the same objects.
- **Text:** every PR body, issue body, review and comment, through `gh api`, every page.
- **Actions logs:** the logs and artifacts of every workflow run that GitHub still keeps, all jobs.
- **Output:** places only: ref or commit + path + line, the PR or comment id, the run + job id. Never the value, not even a part of it.
- **On a hit:** the scan stops at once and reports to pl-lead. **pl-lead writes the rotation card** (a host card for the Proxmox token or the recovery key; a user step for anything of the user). A secret in the history → stop and ask the user (a rewrite is a force-push).
- **The O7 source list (C9):** the review comments of the slice 8 PRs #359 … #384 (`gh api` of each), the "Lows on record" lines of STATUS, ROADMAP rows 33 and 40, D-415, D-433, and the open points of the T-245 and T-253 cards.

## 6. Risks

- **A secret in the git history** (C5a): a fix needs a history rewrite, which is a force-push (forbidden for agents) and a public step: stop and ask the user.
- **The first upgrade path is not tested with the user's data:** the user's install runs an old controller (slice 6 rights). C7 (a) runs that path on `pve-dev` from the user's version (U12); the user's own run (U7) uses `--dry-run` first.
- **No earlier tag:** the attestation and `SHA256SUMS` prove the tarball, not the code before it. The changelog says that v0.1.0 (if the user picks it) is the first release.
- **What the attestation proves (L3 of #370):** where and from which commit the tarball was built, not that the code is good. The release text says so, and says "pre-1.0: the API may still change".
- **`vmbr9` undo after the last NIC proof:** after C8, a NIC regression can only be proven by a new D-379 card.
- **O1 unexplained:** a flaky firewall test can hide a real fault. C9's probe loop (P2) reads every dump; the release notes name it if it stays unexplained.
- **The build is not reproducible across machines (P3):** then the release is the workflow's own artifact, tested on `pve-dev` before the user publishes.
- **One card at a time with three agents:** C7 is long (several hours on the host). The user questions U9, U10, U12 are already asked, so C7 does not wait on them at the end.
