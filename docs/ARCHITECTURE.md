# Architecture

Plumb is one controller service plus one small agent in every guest. This file is the contract for all agents.
Reasons for each choice: `docs/DECISIONS.md` D-018 … D-049. Terms: `docs/BRIEF.md` §3. Proxmox facts were checked against the PVE 9.2 API schema.

## 1. Overview
```
 Browser · API client · (later) MCP
        │ HTTPS :8443 — REST + JSON, SSE events — /api/v1
┌───────▼──────────── plumb (controller, unprivileged LXC) ───────────┐
│  api ─► plan · issue ─► state ─► store (one SQLite file)            │
│            │      │                                                 │
│          link   driver ─► Proxmox REST API (restricted token)       │
└────────────▲────────────────────────────────────────────────────────┘
             │ HTTPS :8444 — JSON, the agent dials out — /agent/v1
 plumb-agent (root, in every VM and LXC): observe · diff · apply · watch
```
- Go, one module, two static binaries: `plumb` and `plumb-agent` (D-018). `plumb` embeds the web UI and the agent binary.
- Web UI: Svelte 5 + TypeScript + Vite single-page app. It uses only `/api/v1`. Its API types come from the OpenAPI file (D-019).
- Storage: SQLite in WAL mode, pure-Go driver, plain SQL, forward-only migrations (D-020).

There are two seams (D-005): `Driver` for Proxmox in the controller, `Resource` for the guest in the agent. Only `driver/proxmox` talks to Proxmox.
```go
type Resource interface {            // internal/resource – runs in the agent
    Observe(ctx) (State, error)      // read the real state
    Diff(observed State) []Change    // Change{Attr, From, To, Risk}; applies the strictness
    Apply(ctx, []Change) error       // idempotent
    Watch() []string                 // paths whose change can mean drift
}
type Driver interface {              // internal/driver – runs in the controller
    FetchImage(ctx, ImageSpec) (ImageRef, error)       // download, verify, make template
    Create(ctx, GuestSpec, Bootstrap) (GuestID, error) // clone, set the enrollment token, start
    Observe(ctx, GuestID) (GuestState, error)          // config, config digest, power, IPs
    Diff(desired GuestSpec, observed GuestState) ([]Change, error) // pure; sets the risk; error for a create-only change
    Update(ctx, GuestID, []Change, *Bootstrap) error // Bootstrap only for re-enrollment; a token is never in a Change
    Power(ctx, GuestID, PowerAction) error; Delete(ctx, GuestID) error
}
```

## 3. Data model (D-021, D-026, D-027)
- The State is a set of **documents**: `kind`, `name`, `spec`. Kinds: `Image`, `Block`, `Target`, `Rule` (slice 2, D-092).
- Documents are YAML in the export and JSON in the database. JSON Schema 2020-12 is the only schema language. It validates documents and defines Block parameters. The UI builds forms from it. The schema files in `internal/` are the only source; the OpenAPI file refers to them (D-043).
- A **Revision** is an immutable, numbered set of documents. Documents are stored once by content hash, so unchanged documents are shared. The newest revision is the desired state.
```yaml
kind: Block                          # blocks/deploy-user.yaml
name: deploy-user
spec:
  params: {required: [ssh_key], properties: {name: {type: string, default: deploy}, ssh_key: {type: string}}}  # JSON Schema
  resources:                         # values are Go text/template strings
    - user: {name: "{{ .name }}", shell: /bin/bash, ssh_keys: ["{{ .ssh_key }}"]}
---
kind: Target
name: web1
spec:
  type: vm                           # vm | lxc
  image: ubuntu-26.04
  guest: {cores: 2, memory: 2048, disk: 20, bridge: vmbr0, ip: dhcp}
  blocks: [{use: deploy-user, params: {ssh_key: "ssh-ed25519 AAAA…"}}, {use: nginx}]
  overrides: {}                      # resource id → attributes. Used by "Accept" and raw mode
```
- The controller **renders** each Target to a flat resource list. A resource id is `type:key` (for example `file:/etc/motd`). Two resources with the same id on one target are an error.
- Block values are Go `text/template` strings over the parameters. Rendering has a time limit and a size limit. Conditions, loops, Block includes and typed values come only when a real Block needs them (§10).
- Order: resources of one Block apply in the listed order. Different Blocks apply in parallel. Package-manager operations share one lock per guest. A Block use has an `id` (default: the Block name); two uses of one Block need different ids (D-048).
- Order between Blocks (D-167 … D-175; contract: T-046, built by T-047 … T-051): a Block can have `spec.after: [resource ids]`, for example `after: [package:nginx]` in `nginx-site`. Each use of the Block starts only when every named resource of the same Target ended `unchanged` or `applied`. When one ended `failed`, `refused` or `skipped`, the use is `skipped` and its steps name the cause. The names are resource ids, not Block names, and the Target has no `after` field. Everything with no such relation stays parallel; list position has no meaning. Render puts the ids on the first resource of the use (`wire.Resource.after`). One function, `wire.Order`, builds the wait graph (listed order inside a use, `restart_on`, `after`) for render and for the agent. An unknown id, an id of the same use and a cycle are errors when the document is saved. The Plan shows `after` on the resource that waits.
- Restart: `service` has `restart_on: [resource ids]`. A Block parameter can set a resource key (for example a file path), so `restart_on` across Blocks names ids that depend on parameters; render checks that each id exists. When a listed resource changes, the agent adds a `restart` change (risk `disruptive`) to the service and applies it after them. The Plan shows this change. A Block can have `spec.restarts: [service ids]`: render adds the resource ids of each use of that Block to `restart_on` of the named services (D-172), so `nginx-site` restarts `service:nginx` of the `nginx` Block. The Plan names the resources that cause a restart (`restart_by`).
- Starter Blocks (`blocks/*.yaml`) are copied into a controller as Block documents; a Plumb update does not change a stored Block. For existing installs (T-088, D-255): the `nginx` and `nginx-site` Blocks before T-088 have `index index.html;` and answer 403 on Debian/Ubuntu with root `/var/www/html`. Replace that line in your stored `nginx` / `nginx-site` Block with `index index.html index.htm index.nginx-debian.html;`. The Plan shows the file change and a restart of `service:nginx`.
- Each resource type states its target kinds (`vm`, `lxc`). The Proxmox settings of a target are one resource, `guest:config`. The driver handles it, not the agent. So plans and issues have one shape for both levels.
- Tables of the first slice (migration 0001): `doc`, `revision`, `revision_doc`, `plan`, `run`, `run_step`, `issue`, `issue_comment`, `binding` (Target → guest id; no Image rows since migration 0006, D-188), `agent`, `enroll_token`, `event`, `user`, `session`, `api_token`. The table `secret` comes with the secret store, in its own migration (§10).

## 4. Change flow and API (D-022, D-023)
1. A client sends a **proposal**: documents to put or delete, and a reason.
2. The controller validates and renders it. It asks the agents and the driver to observe. It stores a **Plan**: one change per resource with `action`, `changes[]` and `risk`.
3. A principal with enough rights **approves**. The controller commits the Revision (author, reason, plan id) and starts a **Run**.
4. The Run works on targets in parallel: guest step, wait for the agent, resource steps. Each step emits events.
- A Plan is stale when the head revision moved. A stale Plan cannot be approved. The agent observes again at apply time. It refuses a change with a higher risk than the approved Plan.
- Rollback, import and "Accept"/"Revert" on an issue all create a Plan. There is no second path.
- Risk classes: `read`, `reversible`, `disruptive`, `destructive`. The risk of a Plan is its highest change.
- One vocabulary in the database, the agent protocol and the API (D-045). Ids of revisions, Plans, Runs and Issues are integers. Plan: `pending`, `approved`, `stale`. Run: `running`, `succeeded`, `failed`. Step: `pending`, `running`, `unchanged`, `applied`, `failed`, `refused`, `skipped`. Issue: `open`, `resolving`, `resolved`. A principal is `user:<name>`, `token:<id>`, `agent:<target>` or `system`.
- A change is `{attr, from, to, risk}`: `from` is the guest now, `to` is the desired state. A sensitive change is `{attr, sensitive, risk}`. The action of a resource (`create`, `update`, `delete`, `restart`) is derived from its changes by one rule, `wire.ActionOf` (D-047).

| Endpoint (`/api/v1`) | Use |
|---|---|
| `POST /session`, `DELETE /session` | Human login and logout |
| `GET /images`, `/blocks`, `/targets`, `/{kind}/{name}` | Read the desired state, plus status per target |
| `POST /plans`, `GET /plans/{id}`, `POST /plans/{id}/approve` | Propose, read, approve |
| `GET /runs/{id}` | Result per target and resource |
| `GET /revisions`, `GET /revisions/{n}/diff`, `POST /revisions/{n}/rollback` | History. Rollback returns a Plan |
| `GET /issues`, `POST /issues/{id}/resolve`, `POST /issues/{id}/comments` | Actions: `accept`, `revert`, `ignore_once`, `ignore_rule` (D-068, D-091, D-092) |
| `GET /events?since=<seq>` | Server-sent events, resumable |
| `GET/POST/DELETE /tokens`, `GET /secrets`, `PUT/DELETE /secrets/{name}`, `GET/POST /export`, `POST /import` | Admin. Token tiers per operation: `api/openapi.yaml` (§12) |
| `GET /rules`, `GET /rules/{name}` | Read the rules (D-092) |

Contract: `api/openapi.yaml` (OpenAPI 3.1, written first). Errors are `application/problem+json`. Times are UTC RFC 3339. JSON fields are `snake_case`.

- **Plan.documents (T-170):** an answer with one Plan lists the document changes that its approval commits (base revision vs the proposal applied, `plan.plannedSets`, the same code as `Approve`), as `RevisionDiff.changes`; references only, never a secret value; bounded at 500 entries / 8 MiB of text (`documents_truncated`). Only for pending and stale Plans (an approved one has its revision diff); a failure leaves the field out with `documents_unavailable: true` and never fails the answer.

## 5. Agent protocol and enrollment (D-024, D-025)
| Call (`/agent/v1`, port 8444) | Use |
|---|---|
| `POST /enroll` `{token, hostname, version}` → `{agent_id, credential}` | Once per agent |
| `GET /poll?wait=30` → `204` or `{id, type, body}` | Long poll. Types: `observe`, `apply`, `watch`, `update`, `seal` |
| `POST /report` `{type, command_id, items[]}` | Types: `result`, `progress`, `drift`, `hello`, `addrs` |
| `GET /binary` | Agent binary for install and update. The pinned TLS link protects it |

- The agent always dials out. A guest needs no open port. A target is online when it polled in the last 90 s.
- Port 8444 uses a certificate from the **Plumb CA** (made at first start). Agents pin this CA. Port 8443 also uses a Plumb CA certificate. The UI is for the LAN only (D-040).
- Enrollment token: random 256 bit, bound to one target, single use, valid 15 minutes, stored as a hash.
- **VM:** Proxmox cloud-init sets network and bootstrap user. `cicustom vendor=` points to one static snippet. The installer writes it once: root-owned, the same for all VMs, never deleted. It holds the CA, the URL and the install command, and no secret. The controller cannot write snippets and has no host mount. The token is the SMBIOS serial of the VM (`smbios1`). The agent reads it from `/sys/class/dmi/id/product_serial` (root only).
- After enrollment the agent disables cloud-init (`/etc/cloud/cloud-init.disabled`). So a later change of the cloud-init data cannot run first-boot steps again. It also has no effect in the guest. So `ip`, the bootstrap user and `disk` are create-only in the slice: a Plan that changes them is refused with a clear message (§10).
- **Images (D-188, D-189):** Plumb keeps no binding from an Image to its template. Every guest create calls `FetchImage` with the Image document of the Run's revision; the driver reuses the template of that name and checksum or makes it again. The create-only attribute `image` is the Image name, which the driver writes into the guest description, so a new checksum or a re-made template changes no guest that exists.
- **Container image versions (T-082, D-234, D-251 … D-253):** the build container comes from the repacked template file; seal runs as a container seal (the upgrade in seal, no cloud-init, no initramfs, no trim; an empty `/etc/machine-id`; a first-boot unit makes the SSH host keys before ssh; the first-boot installer and the agent unit stay, the agent binary and its state go). Before the template call the driver removes `env` and proves that the config, the next view and the pending list hold none; a Target is a full clone that must not inherit `env` and gets its own token. A clone gets no SSH keys from Proxmox: such a Target has no `ssh_keys` (use the Block `deploy-user`).
- **Image versions (D-208, D-221, D-222):** `MakeImage` clears the build values in one config write and regenerates the cloud-init drive, so a version template holds none of the build guest's user-data. Plumb makes only full clones. **Known limit (D-221):** on lvmthin the Plumb token cannot see a linked clone that someone made by hand in Proxmox, so `RemoveImage` removes the template under it; the thin clone keeps its data.
- **Known limit (D-192, D-220, D-223):** a stock Ubuntu 26.04 image used directly by a Target can sometimes stay on DHCP until its first restart due to a boot race. Use DHCP or build the Image with Plumb; built Ubuntu 26.04 Images do not have this limit. Plumb gives no warning at plan time, because an Image is only a URL and a checksum.
- **LXC:** the agent is in the template. The controller sets the token with the `env` option of the container before the first start. The agent reads it from `/proc/1/environ`. The controller then removes the option: the whole `env`, so a variable that a person adds there is removed too (Plumb owns `env` of its containers, D-231).
- **Reported addresses (D-212, D-213, D-216):** the Hello holds the agent's address list (`addrs`), and an `addrs` report sends it again when it changed (checked at every poll round, at most once in 35 s; `addrs_unknown` when it cannot read the list any more) and every 15 minutes. The agent reads it with netlink: interfaces that are up and not loopback, without tunnels, VPNs and container plumbing (`veth`, `tun`, `wireguard`, `vxlan`, `geneve`, `dummy`, GRE/IP tunnels, `docker0`, `podman0`, `lxdbr0`, `incusbr0`, `br-…`, `cni*`, `flannel*`, `virbr*`); the guest's own bridges, bonds and VLANs stay. In a container (only a `veth` left) it reports every up interface (T-038). No loopback, link-local, multicast, IPv6 temporary, tentative, deprecated or DAD-failed address; at most 16. Private ranges and IPv6 ULA are reported. Privacy note: a global IPv6 address made from the MAC (EUI-64) shows that MAC to everyone who can read the Target status. The list is display data only: never used to authorize a call or as a connect target.
- After enrollment the agent sends a per-agent credential (random 256 bit, file mode 0600, stored as a hash) on every call. `seal` deletes it.
- **Agent self-update in the guest (T-091, D-258, D-271 … D-273):** on `update` the agent downloads `GET /binary` from its pinned controller to `/usr/local/bin/.plumb-agent.update` and checks the SHA-256 of the command, then runs `<new> self-test` (30 s, it loads the config and reads the state dir). Then it hard-links itself to `/usr/local/bin/plumb-agent.prev`, writes the marker `/var/lib/plumb-agent/update.json` (`pending`), enables the guard `plumb-agent-guard.timer`, and renames the new binary over `/usr/local/bin/plumb-agent`. A failure up to there changes nothing (Item `agent:binary` `failed`). After the result it exits, and systemd starts the new binary after 10 s. The guard is the old binary (`plumb-agent.prev guard`), one tick every 20 s, and survives a reboot. The new agent confirms after its first accepted Hello (marker and guard go; `.prev` stays). Without that within 5 min (15 ticks), or after 3 restarts of `plumb-agent.service` (crash loop), the guard puts `.prev` back, restarts the agent and marks `reverted`. The agent then sends `reverted` in every Hello until the next `update`. A flock on `update.lock` orders confirm and revert. No resource may touch these files or units (`wire.IsAgentPath`); both seals remove `.prev` and the guard units. **Known limit:** the guard cannot tell a broken binary from an unreachable controller. When the controller is down or unreachable for more than 5 min after the swap, the guard also reverts a good binary; the step then fails with `reverted` (`no-hello`), and a new update Plan installs it again.
- **One-time manual step for agents from before T-091 (D-258):** these agents answer `update` with "unknown command type" and send no capabilities. Run once per guest, as root; the credential, the state and the unit stay:
  - LXC, on the Proxmox host: `pct exec <vmid> -- sh -c 'systemctl stop plumb-agent.service && /usr/local/sbin/plumb-agent-install'`
  - VM, over SSH or the Proxmox console: `systemctl stop plumb-agent.service && /usr/local/sbin/plumb-agent-install`
  - `plumb-agent-install` fetches the agent of the running controller over the pinned link and starts it again. Check: the Target shows the new agent version. A guest without `plumb-agent-install` (made by hand) is re-created instead.
- Re-enrollment (token expired, credential lost): `POST /api/v1/targets/{name}/reenroll` creates a Plan. It sets a new token and restarts the guest (risk `disruptive`). An agent that gets a 401 reads the token source again and enrolls again. A guest without a working agent needs the repair fallback (§10).

## 6. Drift (D-028)
- The same agent binary and the same mechanism run in VMs and LXCs. The agent keeps the desired resource list on disk, so it also checks while the controller is away.
- Fast path: inotify on the parent directory of every `Watch()` path. This includes `/var/lib/dpkg/status` (packages), `/etc/passwd`, `/etc/group` and unit directories. After a 2 s debounce the agent observes only the affected resources. The agent ignores events from its own apply and observes again after it.
- Slow path: a full check every 15 minutes. It covers what has no file event: service state, sysctl, firewall rules. Strictness is part of `Diff` (for example package `present` or `exact`), so the agent sends no noise.
- LXC differences: an unprivileged container cannot change kernel settings. `sysctl` (non-namespaced keys) and kernel modules are VM-only. Proxmox owns hostname and network of a container, so they belong to `guest:config`. Enrollment differs (§5).
- **Outside additions of a container (T-038 §3):** `guest:config` also reads `features`, mount points (`mounts`), devices (`devices`) and raw `lxc.*` lines (`raw_lxc`). Plumb sets only `features: nesting=1` (D-227); anything else is drift with risk `destructive`. "Revert" writes `features` back (active at the next start of the container). Mount points, devices and raw lines can be removed only by root on the host (host H10): a Plan for them is refused with the exact `pct set <id> --delete mp0,dev1` for mount points and devices and, for raw lines, the file `/etc/pve/lxc/<id>.conf` and the lines to remove (the API has no delete for them). "Accept" is refused for all four; "Ignore" works. **Not watched** on a container (review N1 of #169): extra NICs (`net1` and up), a `rootfs` that someone changes to another volume or a bind mount, `hookscript`, and snapshot sections (they act only after a rollback). All of them need root on the Proxmox host, which Plumb trusts (§7).
- Proxmox level: the controller reads each guest config every 60 s. It compares only managed keys, and only when the config digest changed.
- **Address check (D-215):** in the same 60 s loop the controller compares the static `ip` of a Target with the address list its agent reports (§5). It looks only when the agent is online, the list is known and not cut at 16, and no Run works on the Target. A missing address for 2 minutes opens an Issue on `guest:address` (only the ignore actions; `ip` is create-only); the address back for 2 minutes closes it as `gone`. A new mismatch within 1 hour after a close opens the same Issue again, which then stays open for at least 1 hour. The controller stores only the latest list (`agent.addrs`), at most one change per agent in 30 s, also a change to unknown (an old agent, a bad list, `addrs_unknown`); a dropped change leaves the stored list, and the next allowed change wins.
- A drift report opens one Issue per target and resource. Plumb never reverts or accepts by itself. "Accept" writes an override into the Target (new revision).

## 7. Security (D-030 … D-032)
- **Trust boundaries:** client ↔ controller, controller ↔ Proxmox, controller ↔ agent, guest ↔ guest. The controller is the root of trust: it has root in every managed guest. It has no root on the Proxmox host and no host directory.
- **Agents:** a credential is valid for one target only. Agent reports are untrusted input: size limits, schema check, escaped in the UI. The controller removes all values from a reported sensitive change before it stores it (`wire.Redact`). An agent accepts commands only over the pinned TLS link.
- **Enrollment token:** it is visible in the guest config (`VM.Audit`; a container's `env` only with `VM.Config.Options`) and to root in the guest until the next restart. This is acceptable: single use, 15 minutes.
- **Proxmox host users (T-079):** Plumb assumes no untrusted local users on the Proxmox host. An unused token is readable for at most 15 minutes by local users of the host: for a VM on the kvm command line (`/proc/<pid>/cmdline`), for a container in `/var/lib/lxc/<id>/config` (mode 0644, host fact). A user who wins the race makes the real agent's enroll fail; the re-enrollment Plan recovers.
- **Proxmox token:** user `plumb@pve`, token with privilege separation, seven roles, one per ACL path (D-081): `/pool/plumb` (`VM.Allocate`, `VM.Audit`, `VM.Clone`, `VM.Config.{CPU,Cloudinit,Disk,HWType,Memory,Network,Options}`, `VM.PowerMgmt`, `Pool.Audit`); disk storage (`Datastore.AllocateSpace`, `Datastore.Audit`); image storage `plumb-images`, content `import,vztmpl` (D-229; `Datastore.AllocateTemplate`, `Datastore.Audit`); snippet storage `plumb-snippets`, content `snippets` only (`Datastore.AllocateSpace`, needed by `cicustom`); one bridge (`SDN.Use`); the node (`Sys.AccessNetwork`); `/` with propagate 0 (`Sys.Audit`, role `PlumbAudit`, D-240): the thin-pool metadata use for the disk gate (`GET /nodes/<node>/disks/lvmthin` checks `Sys.Audit` on the fixed path `/`, so no narrower path works). Not inherited, so it gives no `/nodes/<node>`, guest-config or storage read. It still lets the token read (never write), cluster-wide: the task list of all users (`/cluster/tasks`); the use metrics of every guest, node and storage (`/cluster/metrics/export`); the guests (IDs, names, volumes) in backup jobs (`included_volumes`) and the backup jobs; the node disk lists and SMART data, the PCI list, `/etc/hosts` and the node config; all datacenter options, cluster status and config, HA, metric-server config (not its token), cluster firewall options, rules, security groups, aliases and IP sets, realm sync jobs, Ceph status, the backup job IDs and comments in the notification matcher values, the cluster name in the login answer. So Plumb sees the IDs, names and use of all guests and the tasks of all users, but no config of a guest outside the pool. An install from before D-240 gets it in a repair run; until then the Plan says "metadata use unknown". No other ACL. No `Sys.Modify`, no `Sys.Audit` on any other path, no `Permissions.Modify`, no `Pool.Allocate`, no console, no guest-agent rights. The disk storage has no `snippets` content; Proxmox needs qemu-server ≥ 9.2.11 and libpve-storage-perl ≥ 9.1.13. The controller LXC is not in the pool, so Plumb cannot change itself or foreign guests. TLS to Proxmox trusts the `pve-root-ca.pem` of the host (the installer copies it) or the system roots.
- **Secrets:** AES-256-GCM. The API can write secrets but never read them. Documents hold references (`secret: name`). An attribute with a secret value is `sensitive`: the agent compares it locally and reports only "changed" or "not changed", so Plans, Issues, events and the database never hold the value or a hash of it. "Accept" is not offered for it. The agent stores its desired list with mode 0600. The master key is a file on its own volume with `backup=0`, so a backup of the LXC holds the database without the key. A restore needs the recovery key. The Plumb CA key is in the normal backup; a new CA needs a new snippet (`install.sh --snippet-only`) and re-enrollment of every agent. The export holds secrets only when the user gives a passphrase.
- **Image build `seal` (D-205 … D-207, T-060):** two independent guards. The controller sends `seal` only to a link `build:<name>`; the agent seals only with the build mark (taken only at a first enrollment from an empty state) and without a `watch` mark (never cleared). Both marks are in the credential file, and no `file`, `directory`, `symlink`, `user` or `service` resource may touch the agent's own paths or unit, also through a link in the guest. **Known limit (n4):** the controller cannot prove that `seal` ran. Root in the build guest holds the build credential and can send a false result; the controller trusts root in a guest already. The real-host check (T-066) searches the template disk.
- **Humans:** local users, argon2id, session cookie (`HttpOnly`, `Secure`, `SameSite=Strict`), origin check, login rate limit, forced password change at first login. Since slice 5 every user has a role on the token scale (`read` < `plan` < `apply` < `admin`, D-329, §17); `admin` is a role, not the tier of every session.
- **API token tiers:** `read` < `plan` (propose, comment) < `apply` (approve up to the `max_risk` of the token, at most `disruptive`). `admin` is the tier of a human session; no token has it (D-046). Only a human session approves `destructive` Plans and manages tokens, secrets and import.
- **Accept is human-only (D-323):** every Plan of origin `accept` (Accept of an Issue, also "Accept as raw for this Target") gets the human-only reason `accept-guest-data`, whatever its risk. It adopts values that a guest reported, and a compromised guest can report valid-looking ones (an SSH key, an apt source). The server sets the reason from the origin, not from the proposal; a new Accept Plan gets it again. Known limit: a `plan` token can copy the observed values of an open Issue into a normal proposal, and an `apply` token can approve it; that is the root-equivalent warning below, not a gap in D-323.
- **Warning:** an `apply` token is root-equivalent on the guests (a `file`, `user` or `service` change can give root). The tiers limit data loss, not privilege. The `command` resource is always `destructive`, so only a human approves it. Every Plan marks it "cannot detect drift".
- **Installer:** runs once as root on the host. It creates role, user, token, pool, the snippet storage with the static snippet, and the LXC. It verifies the tarball checksum and stores the token only inside the LXC.

**Secret store (D-086 … D-090, D-099)**

## 13. LXC Images: the pin (D-224, D-235)
An `lxc` Image names a Proxmox system template by URL and pins its SHA-512. Proxmox serves the templates over http only; the pin is the trust. Copy the pin from the `sha512sum` field of the signed Proxmox appliance index, never from the downloaded file. Creating an `lxc` Image or changing its `url` or `sha512` needs a human approval (`image-recipe`).

## 14. Slice 3: agent update, version gate, new resources (D-257 … D-260, D-266 … D-270)
Wire types: `internal/wire/protocol.go` (`CommandUpdate`, `UpdateBody`, `Hello`, `UpdateRevert`) and `internal/wire/capability.go`. API: `POST /targets/{name}/agent-update`, `TargetStatus.agent_*`, Problem `agent-outdated`.

**Hello (D-266).** A slice 3 agent adds `binary_sha256` (of its running binary), `capabilities` (`commands`, and `resources`: type → the attribute names of its schema, sorted) and `reverted` (see below). An agent without `capabilities` has `wire.BaselineCapabilities`: the six types of slice 2 and no `update`. That list never changes.

**Update (D-258, D-267).** The "update agent" step is the resource `agent:binary` with one change `{attr: version, from, to}`, risk `disruptive`, in a Plan of origin `agent_update` (no document change, no revision). A person or `system` proposes it; a human session or an `apply` token approves (D-257). `system` proposes when an agent says hello with other capabilities than the agent of this controller and lists `update`; at most one pending such Plan per Target. The Run sends `update` with `{plan_id, sha256}`; the sha is that of the binary that `GET /agent/v1/binary` serves. The agent:
1. fetches the binary from its pinned controller to a temp file next to its own, checks the SHA-256, runs `<new> self-test` (exit 0);
2. renames its binary to `.prev`, the new one over it, writes the update marker, sends the result Item `agent:binary` `applied` and exits; systemd restarts it. A failure before step 2 is Item `failed` with output; the old binary keeps running;
3. after a crash loop, or with no successful hello within 300 s, a guard restores `.prev` and restarts. The restored agent sends `reverted {from, to, to_sha256, reason, at}` in every hello until the next `update` command. `reverted` is guest text: the controller drops it when `reason` is not `crash-loop` or `no-hello`, sets `at` to null when it is no RFC 3339 time, keeps `from`/`to` only as printable ASCII up to 64 bytes and `to_sha256` only as 64 lowercase hex digits.

The controller passes the step only when a hello with `binary_sha256` equal to the sent sha arrives within 120 s; a hello with `reverted` fails it; a hello with the old sha after the result fails it only when no hello of the new binary follows within those 120 s (T-108: the old process can still reconnect before it exits). **Lost result (T-102):** the result can be lost when the link breaks at the swap (the old agent exits after 60 s without it). The step then waits for the result and the hellos at once: a hello with the sent sha passes it; a hello with `reverted` (to the sent sha) fails it, but only once the link shows that the agent took the command (the agent drops an older revert when it starts the command, so a revert before that is not this update's), and only when it differs from the revert that the agent reported before the step (a reconnect after a lost poll answer sends the old one again); a hello with the old sha and no revert before a result is a reconnect of the old agent, whose result follows. When the agent took the command and then polls no more (offline, 90 s) for another 120 s with no result and no hello, the step fails. A command that waits untaken keeps the `ApplyTimeout` limit. A failed `agent_update` Run does not put the Target in phase `error` while its agent is online: the old agent works, and `agent_update`/`agent_reverted` show the outcome. Agents from before slice 3 cannot update themselves (`agent_update: manual`): root in the guest stops `plumb-agent` and runs `plumb-agent-install` once (`pct exec <id> -- …` for an LXC, SSH or console for a VM), or re-create the guest.

**Gate (D-259, D-268).** `capabilities` is guest data with limits (`wire.Capabilities.Valid`: ≤ 64 types, ≤ 64 attributes per type, ≤ 16 commands, names of `[a-z0-9_]`, ≤ 64 bytes); the controller treats a list that breaks them as the baseline, before it stores it. `wire.Capabilities.Missing(resources)` is the one rule: each resource needs its type and every attribute that its rendered attrs set; `guest:*` needs nothing. A Plan whose Targets need something that their agent lacks is refused with 409 `agent-outdated` ("update the agent first", `targets`, `missing`) at creation and at approval. Plans of origin `agent_update`, `reenroll` and `build` are not gated (they send no Target resources; a build guest runs the current agent). The Run checks again per Target right before its first observe or apply command, after a create or re-enrollment (D-276); a Target that fails it gets its steps `failed` with the same text and no command. A Target with no hello yet is gated in the Run only; there, an agent without a stored hello counts as the baseline. `system` does not propose again a binary that reverted in this guest (D-275); a second update Plan for a Target is 409 `nothing-to-do` (D-277); an update Plan does not go stale when the head moves (D-278). `system` does not propose again a binary whose update Plan a person discarded for that Target. A Target whose agent enrolled but has no stored hello is gated at planning with the baseline. The update installs the agent of the running controller: after a controller downgrade, `system` proposes a downgrade of the agents whose capabilities differ. `agent_reverted.at` is the time of the hello when the guest's `at` is no RFC 3339 time (the API schema needs a time). Known limit: the gate sees type and attribute names, not values. So a later schema change never widens the values of an existing attribute (a new enum value, a looser pattern); it adds a new attribute instead. The controller never sends an agent a `watch` or `observe` list with a resource that it lacks: it leaves those resources out, and the status shows `required`. Target status: `agent_version`, `agent_update` (`none`, `available`, `required`, `manual`, `unknown`), `agent_missing`, `agent_reverted`.

**New resource types (D-260, D-269).** Schemas in `internal/resource/schema/`; T-093 and T-094 add them to the type table with their code.

| Type | Key | Kinds | Attributes | Risk |
|---|---|---|---|---|
| `apt_repository` | `name` | vm, lxc | `uris`, `suites`, `components`, `architectures`, `key` (inline armored public key), `state` | reversible |
| `unit` | `name` (with unit suffix, not `plumb-agent.*`) | vm, lxc | `content`, `state` | create/change reversible, delete destructive |
| `sysctl` | `name` (dotted) | vm | `value` (string or integer), `state` | create/change disruptive; absent reversible (file removed, running value kept) |
| `command` | `name` | vm, lxc | `argv` (no shell; `argv[0]` absolute), `creates`, `timeout` | always destructive |

- `apt_repository` writes `/etc/apt/sources.list.d/plumb-<name>.sources` and `/etc/apt/keyrings/plumb-<name>.asc`, `Signed-By` names that file; no free options, so `Trusted` and `trusted.gpg.d` cannot be expressed.
- `unit` only writes the file and runs `daemon-reload`; enable and start go through `service` with `restart_on: [unit:<name>]`. A `unit` or `service` resource on a unit whose name starts with `plumb-agent` (any suffix: `plumb-agent.timer` would start the agent's service; also the units a newer agent adds) is refused at save (`wire.AgentConflicts`) and by the agent (D-274). If `apt-get update` fails, `apt_repository` removes its sources file again, so the next run tries again.
- `command` (D-270) has no state and no drift: observe reports `state: absent` while `creates` is missing, so the only change is a create, risk `destructive` (D-031: only a human session approves). It runs as root with `timeout` (default 600 s). An Image whose build Blocks hold a `command` is refused at save, also when a Block gets a `command` after an Image uses it, and the build checks again at start. No stdout or stderr of the program leaves the guest (it can print any secret of the guest): a failure says only the exit status, the timeout, or that `creates` is still missing. The controller shows a `command` change as `destructive` in every Plan (`state.PlanRisk`), also an unverified create and whatever the agent reports. The agent's drift check skips it (`resource.Type.NoDrift`). The program runs with no stdin, stdout or stderr, in its own process group; at the timeout the whole group gets SIGKILL. A child left in the background keeps running but sits in the agent's cgroup, so an agent restart stops it: long-running processes belong in a `unit` and a `service`. The Run waits `ApplyTimeout` plus the sum of the Target's command timeouts (`state.CommandTime`), so a Run never fails while a command still runs; the agent runs one apply at a time and checks `creates` again before it starts the program. A secret in `argv` is refused at save (every guest user can read `/proc/<pid>/cmdline`): write the secret to a 0600 `file` and let the command read it.

**Block attributes at save (T-101).** A proposal checks the resource attributes of every Block that it adds or changes, also when nothing uses the Block (`state.Set.CheckBlockAttrs`): each attribute must be a property of its type's schema and match that property's schema. A string with a template action (`{{`) renders to a string with unknown content, so type and `not` errors are kept for it. Rules over the whole object (`required`, `if`/`else`) depend on parameters and defaults and stay with render. Errors point into the Block (`/put/<i>/spec/resources/<j>/<type>/<attr>`). An unchanged Block is not checked again, so a stored Block from before still loads and never blocks another proposal; a rollback that brings back a changed Block checks it. Import or restore of an export with an old invalid unused Block is refused when that Block is added or changed.

## 15. Slice 4: day 2, safe apply, firewall, raw mode (D-291, D-293, D-295, D-296, D-299 … D-301)
Contract of T-111. Schemas: `internal/state/schema/target.json` (`guest.power`, `guest.tags`, `guest.disk`), `internal/resource/schema/firewall.json`. Wire: `internal/wire/protocol.go` (`CommandGrow`, `GrowBody`, `GrowItemID`, `SafeApplySeconds`, `SafeApplyTypes`, `ReportConfirm`, `Item.RolledBack`), `internal/wire/capability.go` (`LacksCommand`, `GateCommandPrefix`). API: `TargetStatus.phase` `stopped`, `ResourcePlan.confirm_seconds`, `RunStep.rolled_back`, `Issue.raw`, `Issue.source`, `TargetView.raw`, `command:<name>` in `agent_missing` and `agent-outdated`. Code: T-115 (driver, engine), T-116 (agent safe apply, `firewall`), T-117 (agent `grow`), T-118 (web).

**Proxmox day 2 (D-291, D-299).** Three settings of `guest:config`:

| Attribute | Missing means | Change | Risk |
|---|---|---|---|
| `power` (`running`, `stopped`) | not managed (as before: a create starts the guest, a stop outside Plumb is no drift) | start / stop (clean shutdown, hard stop after 2 min, as D-194) | start `reversible`; stop `disruptive`, needs `allow_restart` on VM and LXC (refused at save without it) |
| `tags` (exact set, lower case) | not managed | set the list (`tags` option, `;` separated, sorted) | `reversible` |
| `disk` (GiB) | required | grow only: VM `resize scsi0`, then the agent command `grow`; LXC `resize rootfs` (Proxmox grows the file system) | `disruptive` (cannot be undone) |

- `disk` leaves `driver.CreateOnly`. A proposal that lowers the rendered `disk` of a bound Target below the base revision is refused (422 at `/spec/guest/disk`); a Plan whose desired disk is below the observed one is refused ("Proxmox cannot shrink a disk"). A grow passes the disk gate (D-219, thin-pool overcommit) and needs a running guest (desired and observed `power`); a grow of a VM needs `command:grow` (gate, D-268). A disk bigger than desired (grown in Proxmox) is drift whose Issue has no `revert`.
- Run order on one Target (D-308): the config writes of `guest:config` (cores, memory, bridge, tags; also on a stopped guest, so a start makes them active with no restart), then the start (when `power` goes to `running`), then the disk grow (for a VM the agent command `grow` after the hello), then the agent steps, then the stop (when `power` goes to `stopped`; a failed agent step cancels it). The `guest:config` step stays `running` until the root grow or the stop. A stopped guest with `power: running` has its resources planned unverified, as a new guest. A stopped Target gets no agent command: its agent steps are `skipped` with "Target stopped" (the Run does not fail for them), and its offline agent opens no Issue and gives the phase `stopped`. A new Target with `power: stopped` is created, enrolled and applied, then stopped.
- Drift of `power` (D-309): the guest poll compares the config digest and the power state, so a start or stop outside Plumb of a managed `power` is a `guest:config` Issue; a planned stop is not. Tags compare without case and order.
- Tags: Plumb does not use tags itself. A datacenter `user-tag-access` other than `free`, or a registered tag, can make Proxmox refuse the write with 403; the step fails with the Proxmox text (no new right, D-081).
- `grow` (VM): `GrowBody{plan_id, min_bytes}`. The agent waits up to 30 s for the kernel to see the disk (SCSI rescan), grows the partition of `/` (growpart) and the file system (ext4 `resize2fs`, xfs `xfs_growfs`). It refuses `/` on LVM, RAID, another file system, or a partition that is not the last of its disk; that fails the `guest:config` step with the agent's text, and the bigger disk stays. Item `grow:root`: `applied`, `unchanged` (the partition fills the disk already) or `failed`.

**Safe apply (D-293, D-300).** For the types in `wire.SafeApplyTypes` (`firewall`): value checks, then a transient rollback timer (`systemd-run --on-active=120s`, unit `plumb-agent-firewall-rollback`, loads the confirmed state or deletes the table before the first confirm), marker `<state>/safe-apply.json` (command id, resource, deadline), live apply, a `confirm` report over a new TCP and TLS connection; 2xx within 90 s makes the new state the confirmed one and stops the timer; else the agent puts the confirmed state back and reports `failed` + `rolled_back`. Three independent ways back: the agent itself, the timer (agent dead and not restarted), the boot file (reboot). An agent that starts with the marker restores first, stops the timer, and sends the result of the open apply (the resource `failed` + `rolled_back`, the rest `failed` "the agent restarted during the apply"), so the Run step ends then and not at the apply timeout. The controller answers `confirm` with 204 only for the open apply of this agent and a resource in it (else 409) and stores nothing. The Plan shows `confirm_seconds: 90` on the resource.

**`firewall` (D-295, D-300).** One per Target (`firewall:main`), VM and LXC (T-116 proves nftables in an unprivileged LXC in CI; if it fails, the type becomes `vm` only). The agent owns the table `inet plumb` (input chain, hook priority `filter`) and the boot file `/etc/plumb-agent/firewall.nft` (inside the protected agent paths, so no `file` resource can write it), loaded by `plumb-agent-firewall.service` (`ConditionPathExists=` the file, `After=nftables.service`, `Before=network-pre.target`); the `plumb-agent` prefix rule of D-274 keeps Blocks away from the unit and from the transient rollback timer `plumb-agent-firewall-rollback`. A distro `nftables.service` loads `/etc/nftables.conf`, which starts with `flush ruleset`; the order above loads Plumb's table after it, so an enabled `nftables.service` does not remove it at boot. Rules in this order: loopback, `ct state established,related`, ICMPv6 neighbor discovery and router advertisements, DHCPv6 client (udp 546 from `fe80::/10`), echo requests when `ping`, TCP `ssh_port` from `ssh_sources` unless `allow_no_ssh`, `tcp_ports` and `udp_ports` from `sources`, then `policy`. Ports and sources are comma separated text so that one Block parameter fills them (no typed template values, §3). The SSH rule replaces the save-time refusal of D-295: SSH stays open (from `ssh_sources`; empty = from everywhere) unless `allow_no_ssh: true` is written. The Plan shows the effective rule as a line in `ResourcePlan.summary` ("SSH tcp/22 open from everywhere", "SSH tcp/2222 open from 192.0.2.0/24", "no SSH rule (allow_no_ssh)"). The agent checks every value (ports 1 … 65535, ranges going up, CIDR prefixes) before it arms the timer or writes the marker. Known limits: one firewall per Target, so two Blocks cannot each add ports; ports that Docker publishes pass through `forward` and are not filtered; with `policy: drop`, traffic from a Docker bridge (`docker0`, `br-*`) to a service of the guest itself is dropped unless its port is listed; `ssh_port` defaults to 22, so a Block that moves sshd must set the same port here.

**Raw mode (D-296, D-301).** No new endpoint. `Issue.source` names the Block use that renders the resource; `Issue.raw` is `true` when `source` is set and `accept` is allowed: the UI labels Accept "Accept as raw for this Target". `TargetView.raw` lists `spec.overrides` as `{resource, attrs, source}`. The editor and "Back to the Block" are proposals that change or remove `spec.overrides[<id>]`; the Plan shows the result. Render rules stay (§3): no secret reference and no key attribute in an override; an override of a resource that no longer renders is a render error, so a Block change that removes it is refused until the override goes.

## 16. Slice 4: backup, off-host copy, replace and restore (D-288 … D-290, D-302 … D-304)
Contract of T-110. Format: `internal/backup/format.go`. API (marked `x-plumb-planned` until the code lands): `GET /backups`, `POST /backups` (T-112); `GET /restore`, `POST /restore/confirm`, `POST /tokens/{id}/enable` (T-113); `Token.disabled_at`; Problems `restored-mode`, `backup-running`, `token-revoked`; events `backup.finished`, `restore.confirmed`, `token.enabled`; Issues `guest:missing`, `agent:silent`. Locked users: `POST /users/{name}/password` gives a one-time password, event `user.password_reset` (T-126, D-321). Installer: T-114. Real host: T-122.

**Backup file (D-288, D-302).** `Magic | header length | header JSON | chunks`. The header is clear and holds no secret: format version, time, Plumb version, schema (last migration), `install_id`, `node`, `pool`, `agent_url`, the crypto parameters, a per-file salt and nonce prefix, and the key fingerprint. Data key = HKDF-SHA256(master key, salt, "plumb backup v1 data"); fingerprint = 16 bytes of HKDF-SHA256(master key, no salt, "plumb backup v1 fingerprint"), the same for all backups of one key. Chunks of 1 MiB plaintext, AES-256-GCM, nonce = prefix | index | last flag, AAD = SHA-256 of everything before the first chunk: nothing can be cut, reordered, swapped or changed. Plaintext = a tar with exactly `manifest.json`, `plumb.db` (online snapshot, `VACUUM INTO`), `link/ca.crt`, `link/ca.key`. Never in it: the master key, `plumb.env` (Proxmox token secret), the agent-link server key (made again from the CA).

**Writing (T-112).** `serve` writes `<data>/backups/plumb-<UTC time>.pbk` (dir 0700, files 0600, owner `plumb`): temp name, fsync, rename; then `<name>.sha256`; then the pointer `latest` (`{name, size, sha256}`), each by temp + rename. Schedule: daily at `--backup-time` (UTC, default 03:00, env `PLUMB_BACKUP_TIME`), keep `--backup-keep` (default 7, `PLUMB_BACKUP_KEEP`), manual ones included; only one backup at a time (`backup-running`). The retention never removes the file that `latest` names. Failures are a `backup.finished` event with `result: failed` and show in `last_run`.

**CLI (T-113).** `plumb backup verify FILE` asks the recovery key on a terminal (`--key-file F` exists only for the test host `pve-dev`, D-180, and in tests; the help says so, and the installer never passes it), compares the fingerprint (exit 3 "wrong recovery key" before any decrypt), opens every chunk, checks the tar entries and the manifest sizes, writes nothing; exit 0 when the file restores. It runs on the host (the installer has the binary) and in the LXC. `plumb restore --data DIR --from FILE` runs as user `plumb` after `plumb key restore`: it refuses a data dir with anything but the key volume, verifies the whole file first into a temp dir, then moves the database and the link dir in place and writes the restore record (below). A schema older than the binary migrates at the next `serve` start, as always; a newer one is refused.

**Restore record and restored mode (D-290, D-303).** `plumb restore` stores `restored_at`, the backup header and `restored_mode = true` in the database (new table and `api_token.disabled_at` in migration 0014 or later, T-113; 0013 is T-116), in the same step: deletes every session; sets `disabled_at` on every API token that is not revoked; gives the user `admin` a new random password, which `plumb restore` prints once on its terminal (the installer runs it with its own TTY like `plumb key init`, D-178; it refuses when stdout is not a terminal), so the password of the backup never works again; locks every other user; revokes every unused enrollment token. (Refines D-290, review B1 of #214.) Until `POST /restore/confirm` (human admin session, body `{old_controller_off: true}`):
- API: 409 `restored-mode` for Plan approval, re-enroll, image build, `POST /backups`. Creating Plans works; they wait.
- Engine: no Run starts; Recover fails the Runs of the backup that were running with "interrupted by a restore", without a command; image schedules, retention, `system` agent-update proposals and the backup schedule wait.
- Driver: Plumb calls only its read methods (Observe, guest lists, storage use); a guard around the driver refuses every write in restored mode as a second line.
- Agents: hello, drift and address reports are taken, and Issues open; the only command is `observe`; no `apply`, `watch`, `seal`, `update`, `grow`.
- Tokens: a disabled token gets 401. `POST /tokens/{id}/enable` (human session) enables one, also in restored mode.
The confirm ends all of it at once, sends the current watch list to every online agent (until then they keep the watch list of the old controller), and starts the 10-minute count of `agent:silent`. A `confirm` report of a safe apply that the old controller started gets 409 (no such open apply here), so that guest rolls back by itself (D-300).

**After the restore.** `guest:missing`: a Target whose bound guest Proxmox no longer has (from the first Observe, also in restored mode); never re-created by itself; at its first Observe after the restore the agent credential of that Target is revoked, so a copy of the old disk (another backup, a template) cannot enroll as it. `agent:silent`: a bound, running guest whose agent sent no hello in the 10 minutes after the confirm; the fix is a re-enroll. `GET /restore` lists `unknown_guests`: guests in the pool that no Target, Image version or build is bound to; Plumb never touches them. A guest that a Run created after the backup is such a guest; its agent's credential is unknown, so it gets 401.

**Installer (D-289, D-290, D-304, D-312 … D-314; T-114).** Refinements of T-114: the host reads from the LXC with `pct exec … dd iflag=nofollow` and a size limit instead of `pct pull`, and a copy must start with the backup magic (D-312); the backup settings of serve go into `plumb.env` (`PLUMB_BACKUP_TIME`, `PLUMB_BACKUP_KEEP`, `PLUMB_INSTALL_ID`); `--keep-guests` needs `--plumb-binary` (D-313); `--restore` verifies on the host before any change, so the recovery key is typed twice, and a failed restore can be run again: it removes its half-made LXC first (D-314). `plumb backup now` (T-112) runs beside serve on the same database, not through a socket. Copies are never replaced and are kept by the host's copy time (D-312). Every install and repair run makes `install_id` (a random UUID) in `/etc/plumb/install.state` and `PLUMB_INSTALL_ID` in `plumb.env` when missing, and passes `--backup-time`/`--backup-keep`.
- `--backup-storage ID` (+ `--backup-copy-time`, default backup time + 30 min; `--backup-copy-keep`, default 14; `--backup-max-size`, default 1G): a storage of type `dir`, `nfs`, `cifs` or `cephfs`, else refused. It installs `/usr/local/sbin/plumb-backup-copy` and `plumb-backup-copy.service` + `.timer` (`OnCalendar=*-*-* HH:MM:00 UTC`, `Persistent=true`) and the root-owned directory `/var/lib/plumb-copy` (0755) in the LXC. One run: `pvesm status` says the storage is active, and for `nfs`/`cifs`/`cephfs` `/mnt/pve/<id>` is a mount point; `pct pull` of `latest` to a host temp file (≤ 4 KiB, JSON, `name` matches `NameRE`, size ≤ the cap); `pct pull` of that file to `<path>/plumb-backups/.tmp-<random>` (dir 0700, files 0600, root); size and SHA-256 equal the pointer; rename to the name that the timer builds from the pointer time, never a container path; keep the newest N; `pct push` of `status.json` to `/var/lib/plumb-copy/status.json` (0644 root). Any failed step writes `result: failed` and a short message. `--backup-storage none` removes the timer; `--remove` removes it too; the copies stay.
- `--remove --keep-guests [--backup-to DIR]`: before any change: (1) `pct exec` asks `serve` for a backup (`plumb backup now`, a CLI wrapper of `POST /backups` on the local socket of the LXC) and waits for it; (2) copies it off by the timer path (to the storage of `--backup-storage`, or to `--backup-to DIR`; neither → refused). `--backup-to` is a directory on this host and **not an off-host copy**: if the host disk dies, the copy dies with it; the installer prints this in its plan and asks to go on. The N3 checks (storage active, share mounted) apply to `--backup-storage` only; for `--backup-to` the installer checks that DIR is an absolute, existing, root-owned directory outside `/var/lib/vz` and the Plumb storages; (3) runs `plumb backup verify` on the host copy with the recovery key typed on the TTY (D-178 rules); (4) prints the path. Any failure stops before a change. Then it removes the LXC, its key volume, the copy timer and the Plumb token with its ACLs, and keeps the pool, its guests and templates, the user and its ACLs, the roles, the storages, `plumb-snippets` with the vendor snippet, and a state file with `install_id`, `pool`, `node`, `kept_guests=1` and the old LXC address. `--dry-run` lists each step.
- `--restore FILE --lxc-ip CIDR --lxc-gw IP`: reads the header (clear) and refuses: `--lxc-ip dhcp`; an address that differs from the host of `agent_url`; on a host with a kept state file, another `install_id`, `pool` or `node`; on a host whose pool holds guests without such a state file. A plain install into a pool with guests stays refused. Then it installs as usual (new LXC, key volume, new token with the D-081 ACLs and `Sys.Audit` on `/`, D-240), asks the recovery key on the TTY, runs `plumb key restore`, `plumb backup verify` and `plumb restore`, writes `PLUMB_INSTALL_ID` from the header, and starts `serve` in restored mode. The recovery key never leaves the TTY of the installer.

**Copy rule (D-331, T-148).** On every drift report the controller stores a keyed hash (HMAC-SHA256; key from the master key, own label) per Target, resource, attribute and value, and per element of a list attribute or a list-like string attribute (schema mark `x-plumb-list: ","` or `";"`), after the normalization of `Diff` (migration 0018): one row per (Target, resource, attribute, hash), a repeat only moves its time, at most 10 000 rows per Target, never evicted: a report past the cap, and a reported value with more than 4096 elements (only the first are stored), store nothing more and flag the Target for 30 days (D-331, D-353). While a Target is flagged, an Issue `agent:values` is open (it closes by itself), every Plan that touches that Target is human-only (`accept-guest-data`), and so is every Plan that adds or changes a value on any Target; `guest_data_issues` then names the open `agent:values` Issues. A planned value with more than 4096 elements is human-only too. The observed `ssh` text of `firewall` is compared as the elements of `ssh_sources`. A daily prune removes rows 30 days after their drift ended. When it makes a Plan and again at approval, the server hashes every `to` value (and every added element) of every change and sets `accept-guest-data`, `Plan.guest_data_issues` and `Plan.guest_data_matches` (the Plan's own element; nothing for a sensitive change) on a match. Booleans, numbers and `enum`/`const` values are skipped. **Opaque changes (D-359, T-166):** some observed attributes are a status text, not the guest's value (`firewall.table`, `network.file`, `apt_repository.sources`, `sysctl.file`; `resource.Type.Opaque`). A drift report with one of them stores one keyed hash for the whole type; while it counts (open Issue, then 30 days after the last report, as every row), every Plan that adds or changes a value (not the key) of a resource of that type on any Target is human-only: new elements, and every changed enum, boolean or number as a whole; removals stay free; `guest_data_matches` lists the Plan's new elements. **Lines (D-359):** `file.content` and `unit.content` (`x-plumb-lines`) also hash each line that the desired text does not have, on the report and on the Plan (≥ 8 non-space characters, spaces and tabs collapsed, lower case; the bound counts only new lines). Known limit: only verbatim or normalized copies of a line match; an edited, split or commented line does not. Known limit (review L2 of #248, D-375): `firewall` ports are compared after the merge of ranges, so a copy of a part of a reported range (`8000-8100` reported, `8050` planned) does not match; the type-wide rule catches it only while a live `nft` change of that type counts, not for a range that comes from the boot file. The opaque-type rule is the fail-closed part. An old agent reports the same text, so it fails closed without a version gate. A test makes every resource type either a value type or name its opaque attributes.

Pinned keys, exactly one per source (fingerprints checked from two sources each, PR of T-144). The Proxmox index is fetched as `aplinfo-pve-9.dat.gz`, unpacked (limit 8 MiB), and the detached `aplinfo-pve-9.dat.asc` is checked over the unpacked bytes:

`POST /images/{name}/refresh` and the build schedule make a Plan of origin `pin_refresh` that changes only `sha256` or `sha512`; `Plan.pins` shows source, fingerprint, file, old and new pin, signature time and the last accepted signature time (migration 0019). **`network`, `group` and the generic safe apply (D-332 … D-334, D-348 … D-350; T-150, T-151).** Schemas: `internal/resource/schema/network.json`, `group.json`. Facts: `docs/plans/debian-network-facts.md` (T-160), `docs/plans/netplan-probe.md` (T-149). Before any change the agent sends duplicate-address probes for each new address (IPv4 RFC 5227 ARP probes, IPv6 RFC 4862 neighbor solicitation) on the main NIC and refuses when another host answers.

## 18. Slice 6 part A: settings, Accept to a parameter, MCP, rate limits, live drift (D-360 … D-375)

**Settings (D-361, T-174).** Table `setting` (migration 0020: `key` text primary key, `value` JSON, `changed_by`, `changed_at`). Keys in slice 6: `backup.time`, `backup.keep`. **Accept to a Block parameter (D-362, T-175).** For each change of an Issue on a Block-rendered resource (`Issue.source`), the server takes the attribute's template from the Block of the Target's head revision and parses it with `text/template/parse`. It maps only when the template's root list is `[Text?] [Action] [Text?]`, the action is one `FieldNode` of one identifier (a top-level parameter `p`) without pipe, command arguments or trim markers, and `p` appears in no other node of that attribute. Then: the parameter schema check, and a new render of the Target with `blocks[i].with.p` set: the render must give the observed values for the accepted attributes and the same values as the base render for every other resource and attribute of the Target. **Rate limits (D-365, D-366; T-179, T-180).** API: one in-memory token bucket per API token and kind, chosen by the operation's `x-plumb-rate` mark: `proposal` 30/min burst 30, `comment` 30/min burst 30, `read` 600/min burst 120 (every token `GET` except `/events`). A human session is not limited this way. Over the limit: 429 `rate-limited`, `Retry-After` in whole seconds, nothing done; event `token.rate_limited` at most once per token per 10 min. A test reads the marks: every operation a token can call that makes a Plan has `proposal`, every token `GET` has `read`. Agent link: one bucket per agent for drift reports (120/min, burst 240), checked after the agent's credential and before the body is decoded; over the limit 429 with `Retry-After`, the credential stays valid, nothing is stored; event `agent.rate_limited` at most once per agent per 10 min. **No agent change is needed** (checked for T-173): since D-055 the agent maps 429 to `busyError` (`internal/agent/client.go`), keeps its credential and link, sleeps `Retry-After` (at most 10 min), and `sendDrift` returns no handled items on a temporary error, so `markSent` keeps the items `dirty` and the next flush sends the latest state per resource (`open`, `resolved`). Back-pressure delays drift; it never drops it.

**`firewall-off` (D-368, T-182).** The human-only check compares the render of each touched Target with the base render: a `firewall:*` resource that is in the base and is gone or has `state: absent` in the Plan adds `firewall-off`, whatever made the Plan (proposal, Block or Target delete, override, rollback, import).

**Live drift of `ip` and `nft` (D-367, T-181).** Only while the desired list holds a `network` or `firewall` resource, the agent opens `NETLINK_ROUTE` with the groups `RTMGRP_LINK`, `RTMGRP_IPV4_IFADDR`, `RTMGRP_IPV4_ROUTE`, `RTMGRP_IPV6_IFADDR`, `RTMGRP_IPV6_ROUTE` (for `network`) and `NETLINK_NETFILTER` with `NFNLGRP_NFTABLES` (for `firewall`). A received datagram is a trigger: the agent checks only that it holds at least one netlink header with a sane length, never reads attributes. Debounce 2 s, at most one triggered check per 5 s per type, skipped during the agent's own apply or safe-apply window; the check is the normal `Observe` of every resource of that type. A failed subscribe logs once; the hello field `live_watch: {network, firewall}` (only the types the agent holds) is `false` for it, and the full check every 15 min stays the fallback. The controller shows it as `TargetStatus.agent_live_watch`. CI guest test in the VM job.

**MCP (D-364, T-178).** `plumb mcp` speaks MCP over stdio only. Config: `PLUMB_URL`, the token from `PLUMB_TOKEN` or a 0600 file (`--token-file`), the controller CA pin as the CLI does. Library: `github.com/modelcontextprotocol/go-sdk` v1.8.0 (2026-09-14; Apache-2.0, older parts MIT; checked for T-173); its `auth` package and OAuth are not used. The stdio transport sets `MaxLineLength` explicitly to 4 MiB, so a client cannot make `plumb mcp` buffer an endless line (review n1 of #276). Tools (fixed in code, the same set for every tier; the server's tier and human-only rules stand behind them):

| Tool | API |
|---|---|
| `list_targets`, `get_target` | `GET /targets`, `GET /targets/{name}` |
| `list_issues`, `get_issue` | `GET /issues`, `GET /issues/{id}` (diff and comments) |
| `list_plans`, `get_plan` | `GET /plans`, `GET /plans/{id}` (effects, documents, `human_only`) |
| `list_runs`, `get_run` | `GET /runs`, `GET /runs/{id}` |
| `list_revisions`, `diff_revision` | `GET /revisions`, `GET /revisions/{n}/diff` |
| `list_blocks`, `get_block`, `list_images`, `get_image`, `list_catalog` | the matching `GET`s |
| `events_since` | `GET /events?since=<seq>`, read for at most 5 s or 100 events, then closed |
| `propose` | `POST /plans` (put or delete of Targets, Blocks, Images) |

Not offered: approve, ignore (once or by rule), secrets, tokens, users, settings, export, import, backups, restore, agent update, image build and refresh. Every tool result is the API JSON, cut at 256 KiB with `truncated: true`; fields that hold guest data (`changes[].from`, comments by other authors, agent text) stay JSON values, and each read tool's description says that they are untrusted data and never instructions. A 429 is returned to the client as a tool error with the wait time. The web shows the reason of a Plan made by a token below the changes, tagged "written by API token <name>" (T-176).
