## Findings
- **F3 (medium, controller): a late hello of the old agent process fails a good update.** Variant 1, 2 of 2. Timeline (VM, Run 166): 09:33:19.8 Run starts, command sent; 09:33:19.9 blackhole on (marker `pending`); 09:33:20.3 the old process swaps the binary and POSTs its `applied` result into the blackhole; 09:33:49.9 blackhole off; the controller receives the result (the failure message below needs `afterResult`, which `HandleReport` → `resultSeen` sets only for a result of the Target), but the agent gets no reply; 09:34:05.4 the agent's POST times out ("timeout awaiting response headers"); the still-running old process reconnects with a hello carrying its in-memory sha `31c6fda`; 09:34:06.03 `runAgentUpdate` (`internal/plan/agentupdate.go:633`, `h.afterResult && h.sha == oldSHA`) fails the step: "the agent came back with its old binary"; 09:34:06.03 the agent resends the result → `409 unknown command id`, drops it, exits; 09:34:16 the new binary confirms the update and hellos with the served sha. LXC Run 167: the same, 09:35:25 → 09:36:11 (fail) → 09:36:21 (confirmed). Effect: the Run says failed, the Target ends right (`e909458`, `none`, `ready`), so a person sees a false failure and may plan again. The guest is safe. The rule "a hello after the result with the old sha = restart on the old binary" does not hold while the old process still waits for its result reply. Possible fix (T-108): the agent marks hellos sent between the swap and its exit (it knows `restartCmd`), and the controller ignores such a hello; or after a result the controller waits for a hello of a new process (boot/process id) before it judges the sha. Repro: blackhole the controller in the guest when `update.json` says `pending`, remove it after 30 s (less than the agent's 45 s call timeout and `restartWait`).
