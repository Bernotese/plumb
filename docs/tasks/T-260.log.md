## O9 (a): the D-429 drop after a cut restore Run

- **Today** (`TestCutRestoreRunDropsNoSafetyBackups`, `internal/api/restore_cut_drop_test.go`): a restore Run that a controller stop cut after the restore call ends "succeeded" at the next start, and the start rule makes the re-enroll Plan, but the D-429 drop of the older `pre-restore` volumes does not run. Only the live Run calls `DropSafetyBackups` (`internal/plan/restore_guest.go`); `recoverRestores` does not. The old volumes stay until the next restore that works.
- **Proposal: leave it, with one README line.** It fails safe: more safety backups are kept, none is lost. A drop at start-up would need the Run's own safety volume from the store, and a wrong keep there deletes a backup, which is worse than a full storage. README line: "After a controller stop during a restore, the older safety backups of that guest stay until its next restore that works; you may delete them in Proxmox."

## O9 (b): a re-enroll Plan that survives a head move (written proposal only; nothing built without pl-lead's yes)

- **Today:** `MarkStalePlans` makes every pending Plan stale when the head moves, also the re-enroll Plan that the D-439/D-440 Issue waits for. The person then plans the re-enroll again, which the Issue says (D-440). It is a comfort, not a hole.
- **Change:** a pending re-enroll Plan stays when the head moves, if what it would apply is unchanged: the Target's rendered resources at the Plan's base equal those at the head.
- **What "equal documents" must mean:** the rendered result, not the document text. That means the Target, every Block it uses (also through other Blocks), its Image, its parameters, the secret values that it renders (a rotated secret changes the result although no document changed), and the install facts (bridges, VLANs). Compare by a digest of the rendered resources at both revisions, made by the same code.
- **Risks:**
  - (1) The check and the approve must be one transaction. If the head moves between them, the Plan must be stale at approve time. So the check runs inside `ApprovePlan`, and a failed check makes the Plan stale there.
  - (2) The D-439/D-440 gate reads its proof from the store at approve, as today. A later restore ends the proof (H1 of #374) and must make the Plan stale too.
  - (3) Who may approve stays unchanged.
  - (4) After a Plumb upgrade the render code changes, so a digest across versions can differ. Then the Plan goes stale, which is safe.
  - (5) It touches the approve path, so pl-reviewer reviews it as critical.
- **Recommendation:** not for this release. The way out works today, and the change is on the approve path. Make it a card after the release, if the host runs show that a stale re-enroll Plan happens often.
