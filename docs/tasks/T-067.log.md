## 3. Why D-192 did not reproduce in check (b): it is a race – **sometimes (3 of 5 took the static address)**
Asked by pl-lead after the report. 5 fresh stock Ubuntu 26.04 Targets with the same static address `<static>`, one after another (one guest alive at a time), 20:07–20:15, Runs 64–73; each guest deleted after its facts were read (SSH as the test user over the host jump; read-only).

|---|---|---|---|---|---|---|---|

| r4 | 0.37, 0 | 30 s | yes | `eth0` | `10-netplan-eth0.network` | none | 15 s |
| r5 | 0.72, 0 | 50 s | yes | `eth0` | `10-netplan-eth0.network` | none | 35 s |

With the two guests of check (b) (both static at the first boot): 5 of 7 today; T-015 run 4, T-015 fact (b) and the T-039 baseline (D3) were 3 failures. **Result: sometimes.**

- **Same image:** every import file today and in T-015 run 4 has the SHA prefix `5645d0318ad2` of the pinned SHA-256.
- **Same Plumb settings in every boot today:** `cicustom: vendor=…plumb-vendor.yaml`, `ciupgrade: 0`, `ipconfig0: ip=<static>/24,gw=<gw>`, `nameserver: <gw>`, `searchdomain` (D-187), `cpu: x86-64-v2-AES`, 1 core, 1024 MB. T-015 run 4 had 2 cores and no `searchdomain` (pre-D-187). Since passing and failing boots happened with identical settings, the settings are not the cause.
- **Not host load:** the 1-minute load was 0.15–0.73 and no other VM ran, in failing and in passing boots alike.
- **Cause (from the guest journals):** the initrd starts `systemd-networkd` with the dracut file about 3.8–4.3 s after power-on, and switches to the real root shortly after (kernel ≈ 1.7–1.9 s + initrd ≈ 2.4–2.8 s). **When the DHCP lease arrives before the switch** (r1, r3: about 0.25 s after networkd started), the NIC stays configured and "busy": the kernel names it `ens18`, cloud-init logs `Failed to rename devices: … [busy]` twice, netplan's `10-netplan-eth0.network` (match MAC **and** `Name=eth0`) never matches, the dracut file (`DHCP=yes`) stays in `/run/systemd/network` and wins, and the boot waits about 2 min (network-online). **When the switch comes first** (no lease line in the initrd), the rename `ens18 → eth0` works and netplan's static file applies. So it depends on how fast the network's DHCP server answers, compared with a fixed ~0.3–0.5 s window. The 180 s first boots of T-015 and T-039 are all the failing case.
- **Consequence:** D-192 stays a real fault, but it is intermittent, not "always". The fix of T-039 (dracut without the network modules in a built image) removes the race. The `guest:address` Issue of T-067 is the safety net for stock images; check (b) above proved its open and close path.
