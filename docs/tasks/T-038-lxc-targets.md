## Goal
A Target with `type: lxc` is created from a Plumb template, enrolls with the `env` token and is configured by the agent like a VM.

## Design (decision level – D-097, ARCHITECTURE §5, §6, §12)
- The agent is in the template. The controller checks the Proxmox base template against the checksum of the Proxmox appliance index, repacks it and uploads it through the API. No host access.
- Enrollment: `env` option before the first start, read from `/proc/1/environ`, removed after enrollment.
- `guest:config` owns hostname and network of a container. Kernel-level resources are VM-only.

### 0. Shape in one paragraph
An Image with `type: lxc` names a Proxmox system template by URL and pins its SHA-512 from Proxmox's signed index (no https exists for these files, A2). `FetchImage` downloads it into the controller, checks the pin, appends a small first-boot installer for the agent (no agent binary), the Plumb CA and `agent.json` to the tar stream, and uploads the result as `vztmpl` to `plumb-images`. `Create` makes an unprivileged container with `nesting=1` from that file, with the enrollment token in `env`. At the first boot the installer fetches the current agent from the controller (as on a VM, D-082); the agent reads the token from `/proc/1/environ`, enrolls, and the Run removes `env`. Then everything is the VM flow: Blocks, drift, Issues, delete with revoke.

### 1. Contract and data model (no migration)
- **Image `type: lxc`** (D-224): `url` may be `http://` or `https://`; the pin is `sha512` (128 hex, from the `sha512sum` field of Proxmox's signed index); `sha256` is not allowed for `lxc`. `type: vm` is unchanged (`https://` + `sha256`). Schema: an `if type = lxc then … else …` block (note for T-075: Redocly closes sub-schemas; the `if/then/else` parts need `additionalProperties: true`, see the memory note of `check:api`). The docs list today's values for `debian-13-standard_13.6-1_amd64.tar.zst` and `ubuntu-26.04-standard_26.04-1_amd64.tar.zst` and the host command that prints the `sha512sum` of any template from the index cache that `pveam update` verified (`/var/lib/pve-manager/apl-info/download.proxmox.com`).
- **Who may set the URL** (review S1): creating an `lxc` Image and changing its `url` or `sha512` adds the human-only reason `image-recipe` (D-201, D-235). So only a human session approves a Plan that makes the controller fetch a new address; a token cannot.
- **Target `type: lxc`**: the Image type must match (exists, `state/validate.go:702`). `user` is refused ("an LXC Target has no bootstrap user; use the deploy-user Block"); `ssh_keys` go to `root` with `ssh-public-keys` (D-226). `disk` = root fs size in GB, min 2 (a fresh Ubuntu root fs uses about 0.7 GB, E1). `allow_restart` is accepted and has no effect: `cores` and `memory` are live on a container (C5).
- `ip`, `gateway`, `name`, `disk`, `ssh_keys` stay create-only as on VMs (D-185 A). Reason for `ip`: a live `net0` change keeps the old DHCP address next to the new one until a restart (C5); a `name` change reaches `/etc/hostname` only at a restart (C5). Live changes of these come later.
- `Image.spec.build` for `lxc` is refused ("LXC image builds come later") until T-082 (question 3).
- `ImageStatus.unused_imports` also lists unused LXC template files of the Image, with the `pvesm free <storage>:vztmpl/<file>` line (D-233). The field is then present for an `lxc` Image without `build` too. Contract notes "LXC: T-038" are replaced.

### 2. Template repack (`internal/driver/proxmox/ctpack`, pure Go, no Proxmox)
- Input: the downloaded file, checked against the pinned SHA-512 first; nothing is parsed before the check. Compression by magic: zstd (every Proxmox system template, A1) and gzip; others are refused with the format name. New dependency `github.com/klauspost/compress/zstd`, decoder only (D-225).
- **Byte-exact base** (D-230): the 512-byte blocks of the base are copied unchanged up to the end of the last entry (found with `archive/tar` over a counting reader: after each entry the data end rounded up to 512). GNU headers and the 63 GNU long names of Ubuntu (A3) are never decoded and written again. Then the Plumb entries (USTAR, `./` prefix as the base, uid/gid 0, fixed mtime), then two zero blocks and padding to a 10 240-byte record (A3).
- **Plumb entries — no agent binary** (D-230): `./etc/plumb-agent/` (0755 dir), `./etc/plumb-agent/ca.pem` (0644), `./etc/plumb-agent/agent.json` (0644: `url`, `ca` as PEM text (D3 note), `token_env: PLUMB_ENROLL_TOKEN`), `./usr/local/sbin/plumb-agent-install` (0755, the same script as the vendor snippet of D-082: curl, wget or python3, pinned CA, 10 min retries), `./etc/systemd/system/plumb-agent-install.service` (oneshot, `After=network-online.target`, no `ConditionPathExists`; the script itself exits 0 when the agent runs, then starts the agent), `./etc/systemd/system/plumb-agent.service` (as the snippet) and the two `multi-user.target.wants` links. So a template does not change with an agent release, as VM templates (D-206): no new file per controller upgrade, which matters because the token cannot delete one (B4).
- **Name matching** (review S3): every base name is normalised (strip `./`, `path.Clean`, no trailing `/`). For a Plumb path and each of its parents (`etc`, `etc/systemd`, `etc/systemd/system`, `etc/systemd/system/multi-user.target.wants`, `usr`, `usr/local`, `usr/local/sbin`) the **last** entry of that name decides, because the last one wins at extraction. A hard link or symlink entry *named* like a Plumb path or a parent counts as "exists" or "not a directory".
- **Refuse the base** when: a Plumb path exists in it; the last entry of a parent is not a plain directory; it has a char or block device or a fifo ("the template has device nodes; an unprivileged container cannot make them"; Proxmox templates have none, A3); none of `usr/bin/curl`, `usr/bin/wget`, `usr/bin/python3` is in it; the tar is truncated.
- **Limits** (review S2, D-225): the decoder runs with `WithDecoderConcurrency(1)`, `WithDecoderMaxWindow(128 MiB)`, `WithDecoderMaxMemory(256 MiB)`, and is closed on every path, also on a ctx cancel (no goroutine left after `Stop`, PR #144). The 4 GiB unpacked limit counts the bytes that come out of the decoder, not the tar header sizes; at most 500 000 entries (Ubuntu: 0.63 GB, 27 135 entries, A3).
- These rules give robustness, not a security boundary: the boundary is the pin (§6).
- **Partial binary** (review S4): the script copies the download to a temp name in `/usr/local/bin` (`install -m 0755 "$tmp" /usr/local/bin/.plumb-agent.new`, then `mv`), so a crash or full disk never leaves a half binary under the real name. The vendor snippet of `install.sh` gets the same change (one script text, test of §9).
- Output `.tar.gz` (stdlib, `BestSpeed`, fixed header; about 200 MB for Debian, B3, E1). Same inputs → same bytes. Name `plumb-ct-<image>-<d12>.tar.gz`, `d` = SHA-256 over (pinned SHA-512, CA, agent URL, pack format version).

### 3. Driver (`internal/driver/proxmox`)
- Type of a guest id from `GET /cluster/resources?type=vm` (`qemu|lxc`, `VM.Audit`); a method refuses a guest of the other type. `GuestID` stays the VMID.
- `FetchImage(lxc)`: under the image lock, list `vztmpl` of `plumb-images` (works, B4); a file of the name is reused (trust: §6; S10 retry below). Else: download into `/var/lib/plumb/tmp` (0700; files 0600) → SHA-512 → repack to a second temp file → upload.
- **Size caps and the database reserve** (review B1, D-236): the controller root fs holds the database (`/var/lib/plumb`, 6.7 GB free today, A4). Hard constants: the download stops at **1 GiB** (templates are 130 … 160 MB, A1) and at the `Content-Length` (a body longer than its `Content-Length` fails; a larger `Content-Length` than 1 GiB fails before the first byte); the unpacked tar stops at **4 GiB** (decoder output); the repacked file is at most the unpacked size. **Reserve:** before the fetch and after every 64 MiB written, the fetch checks the free space of `/var/lib/plumb` (`statfs`) and stops when it would drop below **2 GiB**. On every stop both temp files are removed at once. The user sees the step `image:fetch` failed with one text, e.g. "template download stopped: larger than 1 GiB", "… longer than its Content-Length", "… the unpacked template is larger than 4 GiB", or "… the controller disk would have less than 2 GiB free (now 1.8 GiB); nothing was kept". With today's 6.7 GB the Debian path needs about 0.35 GB.
- **Fetch rules** (review S1, D-237): only `http` and `https`; the address that is dialled is checked after DNS (`net.Dialer.Control`), not the name: loopback, link-local (this covers `169.254.169.254`), unspecified and multicast addresses are refused; private LAN addresses are allowed (a local mirror is a valid use, and the response is never shown). No redirects ("the template URL redirects to <host>; put the final URL into the Image"). No auth header, no cookie, no body; a proxy from the environment is not used. An error shows status and size, never the response body. Time limit: 15 min per download. Upload rules from B1: multipart with the field order `content`, `checksum-algorithm`, `checksum`, `file`; a `Content-Length` (no chunked body); `checksum-algorithm=sha256` of the output, so Proxmox checks the copy. Temp files are removed on every path; the start of `serve` removes old `ct-*` temp files. The `ImageRef` is the volid. An upload over an existing name overwrites (B2): the deterministic name makes that harmless.
- **Reuse retry** (review S10): if `Create` from a reused file fails with an archive error of Proxmox (`tar`/`zstd`/`gzip` in the task log), the driver fetches, repacks and uploads the file once more (overwrite, B2) and tries the create once again; a second failure fails the step.
- **Upload space** (review N1): pveproxy buffers the upload in `/var/tmp` and then copies it to `plumb-images`, both on the host root fs (B1, E1); the fetch refuses the upload when the free space of `plumb-images` is below 2 × the file size.
- `Create(lxc)`: `POST /nodes/<node>/lxc` with `ostemplate`, `vmid`, `pool`, `hostname`, `unprivileged=1`, `features=nesting=1` (Ubuntu needs it, D4), `rootfs=<disk storage>:<disk>`, `net0=name=eth0,bridge=…,ip=…[,gw=…]`, `nameserver`, `searchdomain` (D-187), `ssh-public-keys`, `cores`, `memory`, `swap=512`, `onboot=1` as VMs, `description` (image name, version), `env=PLUMB_ENROLL_TOKEN=<token>` (C1, C2: all with today's rights; encode `=` as `%3D`, or send JSON). Then start. A failure after the create removes the half-made container (D-078, T-073).
- `Observe(lxc)`: `config`, `pending`, `status/current`, `interfaces` (addresses without the agent, C7). `TokenPending` = `env` in config or a pending `env` that is not a delete. A container without `unprivileged: 1` is an error "Plumb manages only unprivileged containers" (D-227). **Outside additions** (review S6): `guest:config` owns `features`; a feature other than `nesting=1`, any `mpN`, `devN` or `lxc.*` line makes a `guest:config` Issue (attrs `features`, `mounts`, `devices`, `raw_lxc`; risk `destructive`). "Revert" is offered only for `features` (the token can write it, C/D4, applied at the next restart); for the others the Issue says that a person must remove them on the host or accept them. A pending `delete: env` is neither drift nor "restart needed" (review N5).
- `Update(lxc)`: `cores`, `memory` (live, C5); the bridge of `net0` (live; one bridge per install, D-184); a new token sets `env` (re-enrollment + `Restart`). New method `ClearBootstrap(id)`: `delete=env` with the digest. On a running container it is pending (C4): the config shows no `env` at once; `/proc/1/environ` keeps the used token until the next restart.
- `Delete(lxc)`: `DELETE …/lxc/<id>?purge=1&destroy-unreferenced-disks=1` with the parameters in the query (a body gives 501, C6/C8).
- `ListImages(lxc)`: the `vztmpl` files of the Image; `RemoveImage` is never called for a file (D-233).
- Known host leftover (C8): Proxmox keeps `/var/lib/lxc/<id>/{passthrough,rules.seccomp}` of a deleted container. The token cannot remove them. Host check H11 proves that a new container with the same VMID still starts; if not, the final plan of T-079 adds a rule.

### 4. Engine (`internal/plan`)
- Create of an `lxc` Target: `FetchImage` → disk gate (D-219, root fs on the disk storage; the template file on `plumb-images` is checked by free space of that storage) → `Create` → wait for the hello (as VMs) → new step `guest:bootstrap` = `ClearBootstrap`. A failed clear fails the Run with the text; the token is used and dead, so it is hygiene; the next Run of the Target clears it again (`TokenPending` and no open enrollment).
- Re-enrollment Plan: the VM path (new token in `env`, cold restart), then the clear step.
- **Controller down at the first boot** (review S4): the first-boot script stops after 10 min and runs again only at the next boot. The hello timeout fails the create Run (as for VMs); the recovery is the re-enrollment Plan (new token, cold restart, so the unit runs again). Test in T-080.
- Shutdown (PR #144): the fetch runs inside the Run's context; `Stop` cancels it, the download, repack and upload stop, the temp files go. A cancelled upload can leave `/var/tmp/pveupload-<hex>` on the host (B1); the token cannot remove it: known limit, shown in the docs. Repack time for 0.6 GB is far below the 2 min grace.
- Retention (D-232): unchanged for VMs. For `lxc` Images Plumb has no template container before T-082, so retention only lists unused files (never an error and never a failed step because of a file).
- The disk gate and `restart_needed`: `restart_needed` is always false for `lxc` (C5).

### 5. Agent (`internal/agent`)
- `token_env` in `agent.json`: the agent reads `/proc/1/environ` (root only, 0400, C3; at most 64 KiB; only the named key; NUL list). A missing key is "no token yet" (retry, as today). The value never reaches a log. Only PID 1 has it; systemd does not pass it to services (C3), so the agent must read PID 1.
- `symlink`: `renameat2` → `EINVAL` gives "the file system of <dir> does not support atomic rename (RENAME_NOREPLACE/RENAME_EXCHANGE); on ZFS it needs ZFS 2.2 or newer"; no fallback (D-228). ext4 in a container supports both flags (D3).
- Addresses: `eth0` is `veth` inside (D3); D-216 covers it.
- `/etc/hostname`, `/etc/hosts`, `/etc/resolv.conf` are files that Proxmox rewrites at every start between `# --- BEGIN PVE ---` and `# --- END PVE ---` (D1), not bind mounts. T-078 fixes the comment at `sealfs.go:389`. A Block that manages `/etc/hosts` as a whole file removes that block until the next start: the docs of the `file` resource say so (review N3).
- `seal` in a container: only with T-082 (§11, D-234).

### 6. Security
- **Trust of the base** (D-224): the file comes over plain http (A2). Integrity = the SHA-512 pin in the revision, which a person copied from Proxmox's signed index (or from the Plumb docs), and only a human approves a pin (§1, D-235). A swapped index or a MITM can only make the fetch fail. The tar rules of §2 give robustness; the boundary is the pin. If Proxmox drops an old version from its mirror (404), the error text names the host command that prints the current `sha512sum` (review N4); the docs values are updated per release.
- **Fetch from the controller** (D-237): a new outgoing path from the controller LXC. The rules of §3 keep it away from the controller itself, link-local and metadata addresses, and show no response body, so it cannot read a LAN service through Plumb.
- **Reuse by name** (review S10): the file name is predictable (pin, CA and URL are not secret). Plumb trusts every writer of `plumb-images`: the Plumb token and root on the host. Another holder of `Datastore.AllocateTemplate` there could put a file under the expected name. The installer gives that right to no one else; the docs say so.
- **`nesting=1` in plain words** (review S7): Proxmox then runs the container with the AppArmor profile `lxc-container-default-with-nesting` and lets it mount its own `proc` and `sys`. That is what systemd needs for its own sandboxing (Ubuntu 26.04 has no network without it, D4). The cost: some content of the host's `/proc` and `/sys` (hardware and kernel data) becomes visible inside the container, and the AppArmor rules are less strict. Root in the container is still uid 100000 on the host, with no rights on host files. Proxmox's own web UI turns nesting on for every new unprivileged container.
- **The template holds no secret and no agent:** a public CA, the URL, a script and units. Readers with `Datastore.Audit` may read it.
- **The token:** single use, 15 min, hash, bound to the Target (D-025). Proxmox shows `env` only to holders of `VM.Config.Options` (C2), not in task logs or the access log (C2). In the container only root can read it, only in PID 1 (C3); the clear step removes it from the config at once; the used value stays in PID 1 until the next restart (C4) and is dead. Plumb never puts it in a description, Change, event or log; the replay data leak scan covers `env`.
- **Unprivileged only** (D-227): `unprivileged=1`, `nesting=1`, nothing else; no `lxc.*` keys, mount points or devices. Root in the container is uid 100000 on the host (D3); a `chown` outside the 65 536 map fails (D4): Blocks with such uids fail with the system's error.
- **Repack:** parse only a checked file; limits and parent rules of §2; temp files 0600 in a 0700 directory.
- **Rights of today, a fact we need before T-079's design is final** (review S5): can the token create `unprivileged=0`, set `features` `keyctl|fuse|mknod|mount=…`, or set `mpN`/`devN` with a host path? These rights (`VM.Allocate`, `VM.Config.*`) exist since D-081, so the answer matters even without T-038. T-079 checks it first on the host (H10, moved from T-083) and reports to pl-lead before any driver code; if the token can make a privileged container or a host mount, the user decides about the threat model before the card goes on.
- **Rights:** no new right. The only missing one, `Datastore.Allocate` on `plumb-images` (B4), stays missing for the reason of D-209 (it lets the token change the storage).
- **The dependency:** one module, decoder only, pinned in `go.sum`, `govulncheck` in CI.

### 7. Installer and the upgrade (D-229)
- A new install sets `plumb-images` content to `import,vztmpl`. The start check of D-183 accepts exactly `{import}` or exactly `{import, vztmpl}` (as sets; `pvesm set` reorders lists, G0). With `{import}` it logs a warning, and an LXC Image create fails with "plumb-images has no content vztmpl: run install.sh again (repair run)". VM Targets work either way.
- **Upgrade of an installed Plumb:** run the new `install.sh` with the new `plumb` binary (the normal repair run). It shows the change "plumb-images content import → import,vztmpl" in its plan and asks (D-084), pushes the new binary first, then sets the content, then restarts the controller. The order matters: today's controller refuses the new content with exit 78 (G0). The release notes and `docs/` say this in one paragraph. Do not change the storage by hand before the new binary is in.
- `install.sh --dry-run` prints the `pvesm set` line and says that `pvesm set` rewrites `storage.cfg` and reorders the content lists of other storages (`local`, `local-lvm`: same sets, other order, G0); the installer's own storage rule (D-084) accepts both sets.
- **Rollback** (review S9, D-229): the old binary exits 78 with `{import, vztmpl}` (G0). The start check runs only at start, so the running old process is safe during the window. When the restart of the new binary fails, the installer sets the content back to `import` before it restores the old binary (if it restores it), and prints what it did. A person who puts an old binary back by hand runs `pvesm set plumb-images --content import` first; the docs and the installer's failure text give this line.

### 13. Questions for the user (each with one recommendation)
1. **How Plumb trusts a Proxmox container template.** Proxmox serves these files only over http; the file list is signed and holds SHA-512 sums. Recommended: the Image pins the SHA-512 from that signed list (the Plumb docs give the values for Debian 13 and Ubuntu 26.04, and the UI offers them as a pick list). Other: Plumb reads and checks the signed list itself (a new OpenPGP library in the controller).
2. **Login to a container.** Proxmox has no cloud-init user for containers. Recommended: the Target's SSH keys go to `root`; a named user comes from the `deploy-user` Block. Other: the agent makes the Target's `user` at the first Run.
3. **LXC image builds (Blocks baked into a container template).** Recommended: yes, as the last card (T-082), after plain LXC Targets work on the host, with the reviewer's rule that no enrollment token can reach a template. Other: a later slice.
4. **Old template files.** The Plumb token cannot delete a template file (same as image files, D-209). Recommended: keep it so; Plumb shows the `pvesm free` line per unused file, and a template changes only with a new pinned base, the CA or the URL (not with a Plumb upgrade). Other: give the token `Datastore.Allocate` on `plumb-images` (it could then also change that storage).
