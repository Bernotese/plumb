## Method

- **The items:** at the C5b hold of T-263, pl-backend copied them from the host into `~/.config/plump/t263-c5b/` (0700) on the dev VM. I did not go to the host. The folder held:
  - the two RC tarballs and their `SHA256SUMS`;
  - the DB copy and the Plumb backup (`.pbk`) with its sum;
  - the `plumb.service` journal (7 lines) and, later, the whole journal of the new LXC since its first boot (160 lines);
  - the events (SSE capture) and the 6(2) export;
  - the guest backup listing and one sample guest backup (vzdump, `.tar.zst`);
  - the raw installer outputs.

  The two backups of `~/.config/plump/t263-b62/` were scanned too.

- **Pass 1, exact values:** `scripts/leak-scan.py` (#389) with `--dir` over the folder, `t263-b62` and the sample.
  - Needles: the values in `~/.config/plump` (38 values), among them the three bearers of `t263-secrets.json`.
  - The tool loads only `testhost-admin.pw` as a password. So I made two more runs, each with a values folder that holds one symlink named `testhost-admin.pw`: one to the password file from before R1, one to the password after R1. No copy of a secret was made.
  - `t263-a-recovery.key` does not exist. The T-263 install keeps its key in `testhost-recovery.key`, which is loaded.
  - The tool does not open zstd, so the sample was unpacked with `zstd -dc` into a 0700 scratch folder first. It unpacked whole (685 MB, under the cap).
- **Pass 2, a secret scanner:** gitleaks v8.18.4, built from source into the scratchpad and run with `--redact`. It ran over the folder, the two RC tarballs (unpacked), the sample (unpacked, without `/dev`), `t263-b62` and the whole journal.
- **Pass 3, the bearer shape** (for values the dev VM does not hold): a count of strings shaped like a Plumb bearer, `tok_<16 hex>.<secret>` (`internal/api/secret.go`). It ran over every file of the folder, the unpacked tarballs and the sample, and `t263-b62`.
- **Pass 4, the DB:** each column whose name speaks of a hash, seal, nonce, key, token, password or credential. I read the type, length and byte entropy only, never a value. The DB copy was opened in memory, read-only.
- **The repo part since #389** (merged 2026-11-16T05:40:23Z):
  - a scratch `git clone --mirror` (77 heads, 401 `refs/pull/*`);
  - every issue, PR, comment and review text updated since then (`gh api`), plus every text of PRs 385 to 389 whatever its date, so that nothing falls between T-256 and this card (56 texts);
  - the logs of every Actions run made since then, one run at a time: download, unzip (Python `zipfile`), both tools, delete.

  The hit objects and gitleaks matches were then checked against the objects and commits that are new since #389.

**What a hit would have meant (acceptance point 2):**

- In an RC tarball, any value stops the release. There were none, of any kind.
- In the DB or the encrypted backup, a secret may be there only sealed. In the DB:
  - every token, agent credential, enroll token, session, doc and guest value is a 64-hex hash;
  - the four user passwords are password hashes (97 characters);
  - the repair key is sealed (48 bytes, 12-byte nonce);
  - the `secret` table is empty.

  No plain value of any loaded needle is there, and no bearer-shaped string.

- In the journal, the events, the export or a raw output, a bearer or a password is a finding. There were none.
- The sample guest backup holds the guest's own SSH host keys and the agent's files. That is by design: a guest backup holds the whole guest disk (D-406, README).

**On the host** (pl-backend, a count-only script in the LXC, for the controller's own Proxmox token secret, which the dev VM does not hold):

- 0 in the unit journal, the whole journal, syslog, `plumb.db` and its `-wal`;
- the control count in `plumb.env` was 1.

Agent credentials can be checked only by shape: Plumb stores a SHA-256 hash (`internal/store/agent.go`), and the value lives only in the guests.

**Known limits** (as in T-256):

- text in images;
- other encodings: base32, UTF-16, double URL encoding, JSON `\u` escapes;
- other compression: zstd only by unpacking first;
- encrypted content;
- a value split over two lines or objects;
- the DB copy was made on the host with the SQLite backup API, so it includes what was in the `-wal` (that file itself was also checked on the host for the token secret);
- the master key and the agent credentials are not on the dev VM.
