## D-156 boundary probes

`TestQASecretBindingBoundary` uses the real API, engine, link and fake agent.
The fake's synchronized `Bodies()` recorder stores every raw command body before processing it.
Each case scans all bodies since setup, including after a rejected apply-token approval.
No body holds its canary before human approval. Each case then approves through an admin session,
waits for the guest to hold the exact value, and requires a recorded body with that value.

| Case | Setup and result |
| --- | --- |
| New target | Existing web1; online web2 has no desired-state binding. Plan token creates web2 with the secret. Pass. |
| New resource on an existing target | Existing web1 consumes an old value at `/etc/app.env`. Rotate to a unique canary and move the binding to newly added `/etc/new.env`. Pass. |
| Other secret name on the same resource | Existing web1 consumes app-db. Bind another-name to the same `/etc/app.env` resource. Pass. |
| Rollback restores a binding | Apply a bound revision, apply an unbound revision, rotate to a fresh canary, then propose rollback with a plan token. Pass. Fresh canary prevents earlier approved traffic from hiding a leak. |
| Import-like origin | No import HTTP handler exists at this feature head. Direct `Engine.Propose` with `OriginImport` adds a binding to existing web1; approval remains through the human-session API. Pass. This does not claim coverage of a future import parser or secret import transaction. |

Every case requires `human_only: [secret-binding]` and 403 `human-required` from an apply token.
The owner's `TestSecretNewBindingNotObserved` also passes: new binding omitted, other name omitted,
plain resource still observed, rotation over an existing binding still observed under the accepted D-156 limit.
`TestSecretNewBindingRestart` passes: dependent service has a planned restart and the run succeeds.
Inspection confirms one `newBindings` result drives both the observe filter and human-only reason.
