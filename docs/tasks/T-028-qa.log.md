## Reproduced defects (reported to pl-lead)

### QA-1 — High: complete historical-row replay succeeds

Location: `internal/secret/store.go` (`open`, `Resolve`), migration 0003.

1. Put `a=old-value`. Save its version, nonce and ciphertext.
2. Delete `a`, then put `a=new-value` (the global counter advances).
3. With raw DB access, run `UPDATE secret SET version=?, nonce=?, ciphertext=? WHERE name='a'` using all three saved fields.
4. Resolve `a`.

Observed: `old-value`, error nil. Expected under the card's replay claim: refusal.
The existing `TestTamper/replay_after_delete` replaces only nonce/ciphertext, leaving the new version. It therefore does not cover restoration of the complete historical tuple. The counter remains high but Resolve does not compare the row with independently retained current-version evidence. This is a DB-tampering scenario; it does not provide plaintext recovery to an unauthenticated API client. A decision or implementation change is needed before claiming replay protection.

### QA-2 — Medium: Unicode replacement accounting accepts lossy input

Location: `internal/api/secrets.go`, `replacementsSent` / `secretBody`.

- Human PUT body `{"value":"\ufffd"}` returns 422. Expected 200 and stored U+FFFD.
- Human PUT body `{"value":"�\ud800"}` returns 200. Expected 422 because the lone surrogate must be refused. encoding/json replaces it, changing the supplied text.

`replacementsSent` counts literal U+FFFD twice and does not count the JSON escape. This also gives a literal replacement character room to hide a malformed surrogate. Existing tests cover a literal replacement character and a lone surrogate separately, but miss these combinations.

Both findings were reproduced with temporary Go probes on this branch; the probes were removed. No failing tests or production fixes are included. Reproduction output was retained locally in `/tmp/t028-qa-probes.log`.
