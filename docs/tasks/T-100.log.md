## Findings
- **F1 (medium, controller): a lost `update` result keeps the Run waiting 15 min.** When the agent's `applied` result does not reach the controller (link loss at the swap; here the blackhole came up in the same second as the marker), `runAgentUpdate` waits in `e.command(…, ApplyTimeout)` (15 min) and ignores hellos meanwhile, also the reverted hello of the old agent at 00:25:31. Effect: the Target stays `applying`/busy for 15 min, then phase `error` with "did not answer in time" instead of "went back to its old binary". The guest itself is safe. Suggested fix: while the `update` command waits, a hello of a new connection (the agent restarted) ends the wait and goes to the hello checks (served sha → applied; `reverted` or the old sha → failed). Repro: blackhole the controller in the guest as soon as `update.json` says `pending`.
- **F2 (medium, agent/plan): the first apply of a `unit` + its `service` is always refused.** The Plan observes the service before the unit exists: `state absent → running`. In the Run the `unit` resource makes the unit first, so the agent sees `stopped → running`; `wire.Covers` refuses because `from` differs (`internal/agent/exec.go` `applyStep`, D-075). Every first apply of `docker-compose` (and any Block with a `unit` and a `service` of it) needs a second Plan. 2 of 2 here. CI guest tests did not catch it (their apply does not compare with a Plan observed before the unit existed). Suggested fix: `Covers` treats a planned `from: absent` of a service as covering `stopped`/`inactive` when the unit is made in the same Run (or the service's plan entry is `unverified` when a resource it depends on is a create).
- **Note:** `plumb-agent self-test` prints only `{"version"}`; the T-091 plan said `{version, capabilities}`. The capabilities reach the controller (gate proof above).
- **Note:** `reported_ips` of the LXC with Docker lists Docker's bridge addresses (172.x) before the real address. Display only, but a reader can pick the wrong one (I did, once).
- **Question 4 (D-262):** Docker works in an unprivileged LXC with `nesting=1` and no new right; the only blocker is the `sysctl` in `docker-engine`. A decision is needed: an LXC form of `docker-engine` without the `sysctl` (dockerd sets `ip_forward` in the container's namespace).
