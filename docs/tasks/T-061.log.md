### Finding A: on lvmthin the token sees **no** sign of a linked clone, and `RemoveImage` removes the template
- The linked clone (`POST …/9001/clone full=0`, task OK) has the disk line `local-lvm:vm-9002-disk-0`: lvmthin writes **no** `base-9001-disk-0/` prefix (that form is for file storages). `GET /storage/local-lvm/content?content=images` with the token lists the volume **without** `parent`. So both signs of review S3 are blind on lvmthin.
- `RemoveImage` passed its guard and `qmdestroy 9001` ended **OK**: Proxmox does not refuse to destroy a template whose thin volume is the origin of a clone.
- **Is it harmful? No, on lvmthin (proven by root, 20:18:38–20:18:45):** test template 9050 (1 GB, a marker written at offset 0) → `qm template` → linked `qm clone 9051`. Root's `lvs` shows `vm-9051-disk-0` with origin `base-9050-disk-0` (only root sees it). The clone's config again shows `local-lvm:vm-9051-disk-0` with no base; the token's content list has `parent: null`. `qm destroy 9050 --purge 1` → removed, exit 0. After it, `vm-9051-disk-0` is still active (`Vwi-a-tz--`, origin empty) and reads the marker. Then 9051 was destroyed. An LVM thin snapshot keeps its blocks when its origin goes away.
- **Consequence:** the S3 guard works only where the token sees a sign (file storages with `base-X/vm-Y` lines, and storages that report `parent`). On lvmthin, the default disk storage of the installer, it cannot see linked clones, but the removal does not break them. Open point for pl-lead: (1) write the limit into the docs (card: "else the limit goes into the docs"); (2) the flow test must accept this case, or the recording cannot replay. With the current flow, `TestReplayImageBuild` replays the same failure. The recording is therefore **not** in this PR (see §5).
